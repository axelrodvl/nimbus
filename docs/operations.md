# Эксплуатация

Для тех, кто запускает Nimbus дома или на сервере. Разработка — `docs/DEVELOPMENT.md`, устройство — `docs/architecture.md`.

## Состав и порты

| Что | Где | Порт |
|---|---|---|
| Интерфейс и API (один origin) | контейнер `nimbus`, `NIMBUS_BIND` | 8080 внутри, `NIMBUS_PORT` на хосте (по умолчанию 8000) |
| BitTorrent (входящие) | контейнер `nimbus` | `NIMBUS_TORRENT_PORT` (6881, TCP и UDP) |
| PostgreSQL | контейнер `db` | 5432 внутри, `POSTGRES_PORT` на хосте (для разработки) |

## Тома и данные

- `pgdata` (Docker-том) — база: библиотека, очередь задач, кэш MusicBrainz, настройки, закрепления.
- `./data` → `/data` (`NIMBUS_DATA_DIR`) — скачанные торренты и кэш (`torrents/`), состояние движка (`session/`),
  файлы `.torrent`. **Резервная копия — оба**: том БД (`docker compose exec db pg_dump -U nimbus nimbus > nimbus.sql`)
  и каталог `data/`. Файлы можно скачать заново, а вот закрепления, плейлисты и настройки живут только в БД.
- Восстановление: `docker compose up -d db`, `docker compose exec -T db psql -U nimbus nimbus < nimbus.sql`, вернуть `data/`, `./scripts/start.sh`.
- Обновление: `./scripts/stop.sh && ./scripts/build.sh && ./scripts/start.sh` (миграции БД применяются при старте, только вперёд) или,
  для опубликованных образов, `./update.sh [версия]` (перезапускает стек, только если вышли новые образы) или `./stop.sh && ./start.sh [версия]` (корневые скрипты работают с `deploy/docker-compose.release.yml`; версия — аргумент или `NIMBUS_VERSION`).

## Переменные окружения

Читает `nimbus_core::config` (`backend/crates/core/src/config.rs`) и `main.rs`. Список проверяется скриптом
`scripts/check-docs.ts` (входит в `just check`): переменная в коде без строки здесь — ошибка. Пример — `.env.example`.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `DATABASE_URL` | — (обязательна) | Строка подключения PostgreSQL. |
| `NIMBUS_BIND` | `0.0.0.0:8080` | Адрес и порт HTTP. Не loopback без токена — предупреждение при старте. |
| `NIMBUS_DATA_DIR` | `./data` | Каталог данных (торренты, кэш, сессия движка). |
| `NIMBUS_WEB_DIR` | не задан (в образе `/app/web`) | Каталог собранного SPA; не задан — только API. |
| `NIMBUS_CORS_ORIGIN` | `http://localhost:3000` | Origin для CORS; нужен только в разработке, когда Vite на другом порту. |
| `NIMBUS_API_TOKEN` | пусто | Токен доступа к `/api/*`. Пусто — всё открыто. Выставляя Nimbus в интернет, задайте токен и TLS-прокси. |
| `NIMBUS_MB_USER_AGENT` | `Nimbus/0.3 ( https://github.com/axelrodvl/nimbus )` | Лучше укажите свой контакт (почта или URL): MusicBrainz ограничивает общие User-Agent (503 «throttled», таймауты). |
| `NIMBUS_TPB_ENABLED` | `true` | Провайдер TPB (apibay). |
| `NIMBUS_TORZNAB_URL` | пусто | Адрес Torznab (Jackett/Prowlarr); пусто — выключен. |
| `NIMBUS_TORZNAB_API_KEY` | пусто | Ключ Torznab. |
| `NIMBUS_RUTRACKER_USERNAME` | пусто | Логин RuTracker. |
| `NIMBUS_RUTRACKER_PASSWORD` | пусто | Пароль RuTracker. |
| `NIMBUS_RUTRACKER_COOKIE` | пусто | Cookie вместо пароля (если нужна капча). |
| `NIMBUS_RUTRACKER_PROXY` | пусто | Прокси к RuTracker, например `socks5://host:1080`. |
| `NIMBUS_CACHE_LIMIT_GB` | `50` | Лимит кэша торрентов; закреплённое вытеснению не подлежит и может его превышать. |
| `NIMBUS_SEEDING` | `true` | Раздавать после скачивания. |
| `NIMBUS_SEED_RATIO` | `1.0` | Лимит раздачи (`0` или `none` — без лимита). |
| `NIMBUS_TORRENT_PORT` | `6881` | Порт входящих BitTorrent-соединений; `0` — случайный; занят — движок выберет случайный. |
| `NIMBUS_DEBUG` | `false` | Включает `/api/debug/*` в release-сборке. |
| `NIMBUS_FFMPEG` | `ffmpeg` | Путь к ffmpeg (перекодирование CUE, APE/WV/DSD, ALAC). В образе есть. |
| `NIMBUS_LOG_FORMAT` | текст | `json` — структурные логи. Уровень — стандартная `RUST_LOG`. |
| `NIMBUS_PORT` | `8000` | Только docker compose: порт интерфейса на хосте. |
| `NIMBUS_VERSION` | `latest` | Только `deploy/docker-compose.release.yml`: версия образов GHCR. |

User-Agent и дополнительные заголовки RuTracker (`providers.rutracker.user_agent`, `providers.rutracker.headers`) задаются только в интерфейсе или через `PUT /api/settings`: вместе с `cf_clearance` в cookie они нужны, чтобы пройти Cloudflare-челлендж (см. README, «RuTracker»).

Остальные настройки (источники, лимиты MusicBrainz, производительность, плеер, хранилище) — в интерфейсе («Настройки»)
или `PUT /api/settings`; они хранятся в БД и накладываются поверх значений из окружения.

### Только для тестов (сборка с `test-fakes`)

Образ `nimbus:e2e` (`just e2e`, `just load`) умеет заменять внешние сервисы фейками; в боевой сборке эти переменные
вызывают ошибку старта.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `NIMBUS_FAKE_EXTERNAL` | `false` | Включает фейковые MusicBrainz, Torznab и локальный сидер. |
| `NIMBUS_FAKE_ARTISTS` | 0 | > 0 — синтетический каталог из N артистов вместо фикстур. |
| `NIMBUS_FAKE_ALBUMS_PER_ARTIST` | 15 | Альбомов у артиста. |
| `NIMBUS_FAKE_TRACKS_PER_ALBUM` | 12 | Треков в альбоме (1–99). |
| `NIMBUS_FAKE_SWARM_ALBUMS` | 40 | У скольких первых альбомов есть раздача (маленькие WAV); остальные «не находятся». |
| `NIMBUS_FAKE_LATENCY_MS` | 0 | Задержка каждого ответа фейков. |
| `NIMBUS_FAKE_FAILURE_RATE` | 0 | Доля ответов 503 (детерминированно, по seed). |
| `NIMBUS_FAKE_SEED` | 1 | Seed отказов. |

## Логи

`docker compose logs -f nimbus` (`just logs`). Поля структурные: `album_id`, `torrent_id`, `info_hash`, `job_id`.
Секреты не логируются. При старте предупреждения: заглушка User-Agent, нет токена на нелокальном адресе, нет ffmpeg.

## Диагностика

- `GET /api/health` (открыт всегда) — `db`, `engine {torrents, down_bps, up_bps}`, `jobs {queued, running, failed_24h}`,
  `providers[]` (`state: open` — предохранитель провайдера разомкнут до `open_until`). Это же healthcheck контейнера.
- `GET /api/jobs?state=&kind=` и экран «Настройки → Фоновые задачи» (`/settings/jobs`) — очередь: что идёт, что упало и почему (`last_error`), повтор кнопкой.
- **Что происходит с упавшими задачами.** Задача, исчерпавшая попытки, становится `failed`. `discover_album`, `verify_torrent`
  и `process_cue` дальше ведёт альбом (`on_exhausted` и автоповтор поиска). `import_artist` и `discover_artist` оживляет
  обслуживание: после паузы 15 мин, 1 ч, 6 ч, далее раз в сутки задача возвращается в очередь с нулём попыток — без ограничения
  числа раз. Не оживают задачи с `fatal = true` (артиста нет в MusicBrainz или в БД, неразбираемый payload) — их повторяет только
  кнопка «Повторить». Строки `failed` старше 30 дней удаляются, если они `fatal` или вытеснены более новой задачей с тем же ключом.
- **Что происходит с неудавшимися загрузками на сервер (закреплениями).** Временные сбои (нет места, ошибка движка,
  таймаут запуска) повторяются без ограничения: пауза 1, 5, 15 мин, далее раз в час; сбой БД менеджера закрепление
  вообще не трогает. Если источник не отдаёт данные (нет метаданных; файл не двигается 3 минуты при нуле пиров или
  10 минут при живых), менеджер переключается на следующий источник трека, в том числе на долю CUE-образа; перезапуск того
  же источника — только если движок потерял торрент. Когда источников больше нет, закрепление становится `failed` с
  `error = "stalled"`, повтор через 1, 3, 6, 12, 24, 24 ч (счётчик сбрасывает любой прогресс загрузки). После шести
  циклов — `error = "dead"`, и закрепление пробуется снова раз в сутки без ограничения числа попыток. Постоянный отказ
  источника (плохая ссылка, неверный индекс файла) сначала переключает на другой источник; если его нет — `failed` с
  повтором через сутки. Каждый раз, когда источников не осталось, ставится поиск новых раздач (не чаще раза в 6 ч на
  альбом), а раздачи альбома, которые не удалось проверить, возвращаются на проверку. Закрепление также оживает сразу,
  когда у трека появляется новый источник (поиск, `verify_torrent`, ручной выбор источника), при повторном закреплении
  или кнопке «Повторить». `failed` без расписания не бывает ни в одной ветке.
- `GET /api/acquisition` и «Загрузки → Требуют внимания» — альбомы без раздач, причина, следующий автоповтор.
- `GET /api/downloads`, `GET /api/storage` — торренты, скорость, занято/лимит, закреплённое.
- `/api/debug/*` — только при `NIMBUS_DEBUG=true`.

### Что наблюдать

| Метрика | Норма | Где |
|---|---|---|
| `jobs.failed_24h` | 0 или единицы с понятной причиной | `/api/health`, «Настройки → Фоновые задачи» |
| `jobs.running` без роста `jobs.queued` часами | зависшая очередь: ищите `running` без heartbeat (> 90 с) | `/api/jobs?state=running` |
| провайдер `open` | кратковременно | `/api/health` |
| подключения к БД | меньше размера пула (`nimbus_db::pool_size`), нет `pool timed out` в логах | `pg_stat_activity` |
| память процесса | растёт с числом активных торрентов, после простоя не растёт | `docker stats` |

### Застрявшие состояния

Сервер сам доводит до конца всё, что начал: у каждого состояния «в процессе» (трек ищется, раздача проверяется,
файл качается, импорт артиста идёт) есть исполнитель — задача очереди или цикл обслуживания, — а на случай потери
исполнителя есть страховка. Раз в 10 минут обслуживание проверяет это запросами к БД (инварианты ниже) с отсрочкой
30 минут: состояние, которое дольше получаса остаётся без исполнителя, попадает в отчёт.

- `GET /api/health` → `stuck` — число нарушений последней проверки (`0` — норма);
- `GET /api/jobs/invariants` — сам отчёт (под авторизацией); в интерфейсе — «Настройки → Фоновые задачи», блок
  «Застрявшие состояния» (виден, только когда они есть);
- в логе — `stuck state detected` (`warn`) с кодом инварианта, числом и первыми id.

| Код | Что застряло | Кто должен был починить |
|---|---|---|
| I1 | Трек библиотеки в `adding`, а у альбома нет ни поиска (`discover_album`, `discover_artist`), ни `verify_torrent`, ни `process_cue` | `finalize_stuck_albums` (каждую минуту, через 2 минуты простоя) |
| I2 | Связь альбома с раздачей не проверена, задачи `verify_torrent` нет, поиск альбома не идёт | `requeue_lost_jobs` (каждую минуту) |
| I3 | CUE-образ не разобран, задачи `process_cue` нет | `requeue_lost_jobs` (каждую минуту) |
| I4 | У альбома есть ненайденные треки, поиск не идёт, авто-повтор не назначен (при включённом `search.auto_retry`) | `adopt_orphans` в `retry_missing` (каждые 5 минут) |
| I5 | Упавшая `import_artist` / `discover_artist` ждёт оживления дольше суток | `revive_failed` (каждую минуту) |
| I6 | Задача `running` без heartbeat дольше 90 секунд | `requeue_stale` (каждую минуту) |
| I7 | Задача `queued`, для вида которой нет обработчика | никто: такая задача осталась от другой версии — только отчёт |
| I8 | Закрепление `failed` без расписания повтора (любая причина, включая `dead`) | менеджер загрузок |
| I9 | Закрепление `downloading`, а строки загрузки его файла нет | менеджер загрузок (следующий тик) |
| I10 | Закрепление `waiting_source`, хотя источник у трека уже есть | менеджер загрузок (следующий тик) |
| I11 | Файл докачан, а трек остался `found` | `promote_completed` (каждую минуту) |
| I12 | Артист в библиотеке без альбомов и без задачи импорта | `missing_imports` (каждую минуту, через 2 минуты после добавления) |

**Если нарушение держится** (одна и та же запись в двух проверках подряд) — это дефект, а не состояние, которое нужно
чинить руками: страховка не справилась. Сохраните ответ `GET /api/jobs/invariants` и лог бэкенда за это время
(`stuck state detected` и предупреждения вокруг) и приложите к сообщению об ошибке. Обойти вручную можно повтором
альбома («Загрузки» → «Повторить»), повтором задачи («Настройки → Фоновые задачи») или перезапуском сервера: при
старте зависшие задачи возвращаются в очередь, а загрузки сверяются с диском.

Что отчёт не считает нарушением: выключенный `search.auto_retry`, загрузки на паузе, альбом без раздач (поиск
повторяется по расписанию, до раза в 30 дней), закрепление `dead` (все источники без сидов: повторяется раз в сутки) и
задачи с окончательным провалом (`fatal`).

### Остановка

По SIGTERM/Ctrl+C процесс сразу отменяет токен остановки: воркеры перестают брать задачи, стримы и WebSocket закрываются, HTTP-соединениям даётся 5 с на завершение, затем их обрывают. Параллельно воркеры (до 10 с) возвращают свои задачи в очередь, затем сохраняется сессия торрент-движка; в логе — `shutdown complete`. Всё занимает до ≈ 15 с, поэтому у сервиса `nimbus` в compose-файлах `stop_grace_period: 30s` (по умолчанию Docker шлёт SIGKILL через 10 с). Не сокращайте его: при SIGKILL задачи возвращаются только через `recover_orphans` (и засчитываются как падения, см. `max_crashes`), а состояние движка и DHT не сохраняется.

### Типичные неполадки

| Симптом | Причина и что делать |
|---|---|
| Альбом «не найден» | Нет раздач или все мертвы: «Загрузки → Требуют внимания» покажет причину; «Повторить», добавить источник (Torznab, RuTracker), указать свой magnet. Автоповтор идёт сам по расписанию. |
| Трек долго не начинает играть | Холодный старт 5–30 с (поиск пиров и метаданных). Нет пиров — трек остаётся `found` без движения; проверьте проброс `NIMBUS_TORRENT_PORT`. |
| Импорт артиста идёт минуты, MusicBrainz отвечает 503 | Задайте `NIMBUS_MB_USER_AGENT`; для большой библиотеки поднимите своё зеркало MusicBrainz (README). Импорт повторяется сам. |
| `401` на всех запросах | Задан `NIMBUS_API_TOKEN`, а клиент без токена: войдите на `/login`. |
| Нет звука из CUE/APE/DSD | Нет ffmpeg: в Docker он есть; снаружи — `NIMBUS_FFMPEG`. |
| Бэкенд не стартует: «cannot connect» | БД ещё поднимается или неверный `DATABASE_URL`; бэкенд ждёт и повторяет. Во время остановки БД API отвечает 503 и возвращается сам. |
