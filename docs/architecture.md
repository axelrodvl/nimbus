# Архитектура

```
Браузер (React SPA, PWA) ──REST──► Rust API (axum) ──► PostgreSQL
   │   ▲                            │   │
   │   └──────── WebSocket ─────────┘   ├──► MusicBrainz API / Cover Art Archive
   │                                    ├──► Провайдеры: TPB (apibay), RuTracker, Torznab
   └── <audio src=/api/.../stream> ─────┴──► librqbit (торрент-движок) ──► диск (кэш)
```

Два контейнера: `db` (PostgreSQL) и `nimbus` (бэкенд + собранный SPA). Бэкенд сам раздаёт файлы клиента
(`NIMBUS_WEB_DIR`, в образе `/app/web`; `crates/api/src/web.rs`): всё не под `/api/` — статика, а для навигации по
маршрутам SPA — `index.html`. Один origin, CORS не нужен. Обратный прокси с TLS — по желанию (`deploy/Caddyfile`).

## Крейты бэкенда

`core` (модели, конфиг, события, настройки) · `db` (миграции, репозитории) · `musicbrainz` · `trackers` (провайдеры) ·
`matcher` (файлы ↔ треки, CUE) · `torrent` (обёртка над librqbit) · `library` (добавление в библиотеку) ·
`worker` (очередь задач и обработчики) · `api` (axum, OpenAPI, стриминг).

## Жизненный цикл трека

```
 добавлен ──► [adding] ──(файл сопоставлен)──► [found] ──(файл полностью скачан)──► [ready]
                 │
                 └──(кандидаты исчерпаны)──► [not_found] ──(retry / свой magnet)──► [adding]
```

- `adding` — идёт поиск раздач / верификация (прогресс — событие `job.progress`).
- `found` — в какой-то раздаче найден файл, трек можно стримить.
- `not_found` — причина в `status_reason`: `no_torrents`, `dead_torrents`, `no_match`, `search_failed` (поиск не удался до исчерпания попыток).
- `ready` — файл целиком в локальном кэше (вытеснение кэша возвращает `ready → found`).

## Конвейер

1. **Поиск** — `/api/search` → MusicBrainz (кэш в БД). Лимитер MB (`musicbrainz.*` в настройках, шаг 30): token bucket
   (`rate_per_sec`, `burst`) + семафор `max_concurrent`; фоновые запросы не берут последний токен и уступают
   интерактивным (ожидание на `Notify`, без опроса); на 503/429 темп ×0.5 (не ниже 0.2/с), каждые 30 успехов ×1.25
   до заданного, `Retry-After` паузит всех. Для зеркала (`base_url` не `musicbrainz.org`, остальное по умолчанию)
   `effective()` снимает лимит и ставит `max_concurrent = 8`; `MbClient::reconfigure` применяет значения на лету.
   Кэш `mb_cache`: просроченная запись отдаётся при `RateLimited`/сети/5xx (stale-if-error) и удаляется
   обслуживанием не раньше чем через 30 дней после истечения.
2. **Добавление** — `POST /api/library` → артист/альбом/треки (`adding`) → задача `discover_album` (альбом, трек)
   или `import_artist` (артист).
3. **Потоковый импорт артиста** (шаги 29–30). `import_artist` в **начале** ставит `discover_artist` (поиск дискографий
   идёт параллельно импорту из MusicBrainz), затем получает дискографию пачками (`artist_releases_bulk_filtered`: список
   групп + browse релизов с треклистами по ~25 на запрос; недостающие группы добираются по одной, параллельно;
   при неподдерживаемом ответе — прежний путь «запрос на группу»), а затем после **каждого** добавленного альбома — в той же транзакции —
   `discover_album` (приоритет `NORMAL`). В конце ничего не ставится, искусственных пауз (`run_after`) нет:
   порядок работы задаёт только приоритет очереди и параллелизм (`performance`).
4. **Discover.** `discover_album`: сперва привязывает к альбому уже найденные дискографии артиста
   (`artist_torrents` → `album_torrents`), затем ищет у провайдеров (запросы идут параллельно), ранжирует и ставит
   `verify_torrent`: первые `EARLY_WAVE = 3` раздачи — с приоритетом `discover + 1`, остальные — тем же; если все
   треки уже найдены — `BACKGROUND`. `discover_artist` ищет дискографии, запоминает их за артистом
   (`artist_torrents`, чтобы привязать к альбомам, импортированным позже), привязывает к альбомам, уже лежащим в
   библиотеке, ставит `verify_torrent` для новых пар и финализирует альбомы артиста. Порядок «альбом раньше
   дискографии» и «дискография раньше альбома» равнозначны: привязка идёт и там, и там (`ON CONFLICT DO NOTHING`).
5. **Verify** — список файлов из `.torrent` в БД или от librqbit по magnet (без скачивания) → matcher →
   `track_sources` → `found` / `not_found`. Запись результатов — пакетом, в одной транзакции под блокировкой
   альбома (`insert_many` / `ensure_primaries` / `mark_found`: константное число запросов, не N+1).
   Альбом не объявляется `not_found`, пока активна (`queued`/`running`) задача `discover_album` альбома
   **или** `discover_artist` его артиста; закончившись, `discover_artist` сам финализирует альбомы артиста.
   CUE-образы разбирает `process_cue`: 8 попыток с паузами 1, 2, 5, 10, 20, 30, 30 мин (раздающий может быть
   офлайн долго). Если попытки кончились на временной причине, кандидат получает `failed` (не блокирует альбом),
   и следующий повтор альбома (авто или ручной) разбирает образ заново; битый CUE (`Fatal`) — окончательно.
6. **Play** — `GET /api/tracks/{id}/stream`: качается только нужный файл, куски в приоритете от текущей позиции, ответ `206`.
   По завершении — `ready`. Для CUE/экзотических форматов — перекодирование ffmpeg в FLAC.
7. **Кэш** — задача `evict_cache` по лимиту (`NIMBUS_CACHE_LIMIT_GB` / настройки), не трогает активные стримы и prefetch.

### Провайдеры торрентов

Каждый провайдер ходит за выдачей под лимитером `min_interval` (темп) **и** `max_concurrent` (семафор на время
HTTP-запроса): TPB/apibay — 250 мс и 4; Torznab (свой индексер) — 100 мс и 8; RuTracker — 1 с и 2 (сайт банит за
напор — не снижать). Поверх — `ProviderRegistry`:

- **Таймауты:** запрос — 12 с, соединение — 5 с.
- **Повторы внутри запроса:** сеть, таймаут и 5xx повторяются дважды (0,3 с, 0,6 с) — единичные сбои публичных трекеров
  не доходят до очереди и не считаются неудачей провайдера; 429, блокировка и авторизация не повторяются.
- **Предохранитель** на провайдера: 5 подряд неудачных запросов (после повторов; сеть, таймаут, 5xx, 429) или любая ошибка
  авторизации размыкают его на 60 с (повторные срабатывания подряд — 2, 5, 10 мин); пока он разомкнут, `search_all` отдаёт
  `ProviderError::CircuitOpen` без запроса. После паузы уходит один пробный запрос: успех замыкает, неудача
  удлиняет паузу. Состояние — в `GET /api/health` (`providers`).
- **Кэш запросов:** одинаковый запрос к тому же провайдеру в пределах 10 мин не повторяется (ключ — источник +
  нормализованный текст и структурные поля; LRU на 512 записей; одновременные одинаковые запросы объединяются;
  ошибки не кэшируются). `reload` (смена настроек провайдеров) сбрасывает кэш и предохранители.
- Вход в RuTracker — single-flight: параллельные запросы, увидевшие разлогин, перелогиниваются один раз.

`discover_album` уходит в `Retry` (через 10 мин), только если кандидатов нет совсем, а провайдеры падали или
разомкнуты; иначе работает с тем, что есть.

## Очередь задач и события

Задачи лежат в таблице `jobs` (`LISTEN/NOTIFY` + опрос, повторы с backoff). События публикуются в `EventBus` и
транслируются клиентам через `/api/ws`.

- **Приоритет** (`jobs.priority`, больше — раньше): `INTERACTIVE = 10` (действия пользователя), `NORMAL = 0`
  (массовый импорт), `BACKGROUND = -10` (резервные источники, авто-повторы, вытеснение кэша). `claim` берёт по
  `priority DESC, run_after, id`. Повторная постановка с бо́льшим приоритетом поднимает приоритет ожидающей
  (`queued`) задачи с тем же `dedup_key`. Порождённые задачи наследуют приоритет родителя (`ctx.priority`).
- **Heartbeat.** Пока обработчик работает, раннер раз в 15 с обновляет `heartbeat_at`; задача `running` без
  heartbeat дольше 90 с считается потерянной: `requeue_stale` возвращает её в `queued` (попытка **не**
  возвращается — «ядовитая» задача исчерпает попытки), а исчерпавшая попытки становится `failed`.
- **Восстановление при старте.** `WorkerPool::start` до запуска воркеров возвращает в `queued` всё `running`
  и возвращает потраченную попытку (допущение: на одну БД работает один экземпляр воркеров).
- **Отмена и остановка.** `JobCtx.cancel` срабатывает при остановке пула; обработчики оборачивают ожидания в
  `ctx.run(...)` и возвращают `JobError::Cancelled` — задача уходит в `queued` без траты попытки. Не успевшие за
  `shutdown_timeout` задачи прерываются, их строки возвращаются в `queued`.
- **Исчерпание попыток.** Когда задача окончательно стала `failed` (в том числе `Fatal` и потерянная воркером),
  вызывается `JobHandler::on_exhausted(…, fatal)` (`fatal` — причина окончательная, а не исчерпание на временных ошибках) — он приводит данные в согласованное состояние (раздача помечается
  проверенной, треки без источников — `not_found`, кандидат CUE закрывается, UI получает `library.changed`).
- **Параллелизм** — `settings.performance` (`discover_workers`, `verify_workers`, `import_workers`,
  `metadata_concurrency`, 1–64; `metadata_timeout_secs`, 5–300);
  читается при старте, `PUT /api/settings` возвращает `restart_required`. Пул БД: `10 + воркеры`, не меньше 20.
- **Метаданные торрентов** (шаг 28). Готовый `.torrent` хранится в `torrents.torrent_file` (BYTEA, ≤ 8 МБ; в модель
  `Torrent` не грузится — только флаг `has_torrent_file`). Источники байтов: Torznab (`resolve` уже скачал файл),
  `fetch_metadata` движка (`ListOnly.torrent_bytes`), торрент, добавленный в движок по magnet (`FileProvider::torrent_file`),
  дозаполнение из сессии librqbit при старте. С байтами `verify` разбирает список файлов без сети
  (`parse_torrent_file`), а воспроизведение добавляет торрент по `TorrentRef { magnet, torrent_file }` без ожидания
  DHT. Сетевой путь ограничен семафором `metadata_concurrency`; повторы после таймаута — через 1, 5 и 30 минут,
  следующая неудача — `dead`. Magnet без `tr=` дополняется публичными трекерами при добавлении в движок (в БД не
  меняется); таблица маршрутизации DHT лежит в `{data_dir}/session/dht.json`.
- **API**: `GET /api/jobs`, `POST /api/jobs/{id}/retry` (см. `docs/api.md`).

## Приобретение альбомов

Шаг 32. Состояние **вычисляется** запросом по трекам с `in_library` (`db::repo::acquisition`), не хранится.
Приоритет при совпадении: `searching` (есть `adding`) > `downloading` (есть `downloads` без `completed_at` у файла
основного источника трека) > `partial` (есть `not_found` и `found/ready`) > `missing` (только `not_found`) >
`available` (всё `found/ready`, не всё `ready`) > `downloaded` (всё `ready`).

Таблица `album_search_state` хранит историю поиска. `discover_album` отмечает начало (`last_started_at`) и
число кандидатов/ошибки провайдеров (`[{source, error}]`). Поиск **заканчивается** там, где альбом финализируется
(`verify::finalize`, `mark_not_found` в discover): когда нет непроверенных раздач и активных discover. Тогда
`finish_search` в той же транзакции под блокировкой альбома ставит `attempts += 1`, `last_finished_at`,
`last_outcome` (`found` / `partial` / причина `not_found`) и расписание. Запись срабатывает ровно один раз на поиск:
только если `last_started_at > last_finished_at`. Поиск без начала (ручной magnet) состояние не трогает.

**«Не смогли спросить» ≠ «не найдено».** Если поиск ничего не дал, а провайдеры отвечали ошибками, `discover_album` и
`discover_artist` не делают вывод «раздач нет»: пока предохранитель лишь отключил провайдеров, задача **откладывается**
(`JobError::Defer`, до закрытия предохранителя, попытка не тратится; не дольше 6 ч от создания, затем — исчерпание);
при ошибках провайдеров — повтор через 30 с, 2, 5, 10 мин. Только после последней попытки треки получают `search_failed`.

**Авто-повтор.** После неудачи `next_retry_at = now() + backoff(auto_retries)`: 6 ч, 1 д, 3 д, 7 д, далее 30 д;
для `search_failed` (инфраструктура, а не отсутствие раздач) — 10 мин, 30 мин, 2 ч, 6 ч, далее сутки.
`found` сбрасывает `auto_retries` и расписание. `maintenance_loop` раз в 5 минут (`WorkerConfig::retry_missing_interval`),
если `search.auto_retry`, ставит `Job::RetryMissing`: он в одной транзакции сначала усыновляет альбомы без
расписания (`adopt_orphans`: нужен повтор, нет активного поиска, последний поиск старше 6 ч; `warn` в лог), затем берёт
до 200 просроченных альбомов, которым нужен повтор — есть `not_found`-трек и ничего не ищется, в том числе при
докачке найденных треков (`take_due`, `SKIP LOCKED`; `auto_retries += 1`, `next_retry_at = NULL`), возвращает `not_found`
треки в `adding` и ставит `DiscoverAlbum` с приоритетом `BACKGROUND`. Просроченные записи полностью найденных
альбомов просто сбрасываются; `finish_search` создаёт расписание и для поиска, который не успел начаться. Повторный поиск проверяет только новых кандидатов (`album_torrents.verified`) и
раздачи, возвращённые `reset_dead` (авто-повтор сбрасывает «мёртвые» раздачи: раздающий мог быть просто офлайн). Смена провайдеров (`PUT /api/settings`) назначает `next_retry_at = now()`
всем альбомам, которым нужен повтор.

**Событие `acquisition.changed { album_id }`** публикуется `EventBus` при любом `track.status` альбома и при записи
итога поиска (то есть чаще, чем меняется вычисленное состояние); коалесцируется на шине: первое сразу, остальные в
пределах 500 мс — одно замыкающее.

## Загрузки на сервер

Шаг 33. Таблица `pinned_tracks` (`track_id`, `album_pin`, `state`, `error`, `retries`) хранит **закрепления**; состояние
`queued → downloading → done`, `waiting_source` (у трека ещё нет `found`-источника), `failed`. Закрепление привязано к
треку, а не к файлу: файл вычисляется по primary-источнику в момент работы, поэтому смена primary
(`PUT /api/tracks/{id}/source`, failover) возвращает закрепление в `queued` (в `track_sources::set_primary`, в той же
транзакции). Агрегат по альбому (`AcquisitionItem.download.state`) считается в SQL, а вычисляемое состояние приобретения
(`downloading` — любая незавершённая загрузка основного источника, в том числе стрим/prefetch) осталось как было.

**Менеджер** (`api::download_manager`) — фоновая задача под супервизором, как `Watcher`: тик раз в секунду, будильник
`DownloadHub::wake` (API) и событие `track.status → found`. Паника в тике логируется, менеджер создаётся заново;
отмена проверяется между тиками. Тик:

1. `failed` старше часа возвращается в очередь (до 5 раз); `downloading` при старте процесса → `queued`;
2. `waiting_source ⇄ queued` по наличию источника и статусу трека; файл с `completed_at` → `done`
   (сам `found → ready` делает `Watcher`); `done` с пропавшим с диска файлом — снова в очередь;
3. зависание: файл не двигается `stall_timeout` (10 мин) → следующий источник трека (общая с `failover` стриминга
   функция `next_source`; источники, на которых уже зависало, не повторяются — по кругу не ходим), старый файл
   освобождается `release_unneeded`; источников нет → `failed("stalled")`;
4. запуск: `queued` группируются по торренту, одновременно активны не больше `performance.download_concurrency`
   торрентов; все файлы торрента выбираются одним `ensure_files`; торрент, который уже качается, берёт новые файлы без
   нового слота; создаются строки `downloads`; ошибка запуска → `failed` с причиной (`storage: …`);
5. пауза (`settings.runtime.downloads_paused`): новые не стартуют, торренты только-ради-закреплений — на паузе;
6. `download.progress` (раз в секунду на альбом) и живая статистика `Live` для API; `acquisition.changed` — при смене
   состояния любого закрепления.

**Защита от вытеснения.** `evict_cache` пропускает файлы — primary-источники закреплённых треков; если закреплённое
превышает лимит, вытеснение останавливается с `warn`, а `GET /api/storage` показывает `over_limit`.
**Снятие закрепления** (`download_manager::release_files`): недокачанное отменяется, скачанное остаётся или (по
`delete_files`) удаляется, если файл не нужен другому закреплённому треку и не играет.
**Автозагрузка** (`storage.auto_download = "added"`): `LibraryService` закрепляет добавляемое в той же транзакции,
что и `in_library`; удаление из библиотеки снимает закрепления.

## Синхронизация клиента

Шаг 34. Контракт и формат — `docs/api.md` («Синхронизация»). Устройство: миграция `0012_sync.sql` добавляет
`sync_txid` в пять таблиц (`artists`, `albums`, `tracks`, `playlists`, `playlist_tracks`) с триггером `sync_stamp`
(`BEFORE INSERT OR UPDATE`, ставит `txid_current()` и шлёт `pg_notify('nimbus_sync')`), таблицу надгробий
`sync_tombstones` и триггеры уровня оператора на `track_sources`/`track_plays`, «касающиеся» треков (производные поля).
Репозиторий `db::repo::sync` — снимок (`begin_snapshot`, потоковые выборки), дельта (`changes_since`), курсор, чистка
надгробий; общие SQL-выражения `needs_confirmation`/`transcode` вынесены из `views.rs` макросами и используются и
старым API, и синхронизацией. `api::sync` — DTO, обработчики и `spawn_sync_poker`: `PgListener` на `nimbus_sync` в
отдельной задаче (чтение сокета не прерывается таймером), коалесцер шлёт `sync.poke` в `EventBus` не чаще раза в 300 мс
(первое сразу, внутри окна — одно замыкающее); при разрыве соединения — переподключение и один `sync.poke`. Снимок
пишет задача-источник, владеющая транзакцией и отдающая куски через `mpsc`; уход клиента или зависший читатель
(60 с) завершают её (счётчик `AppState::sync_tasks`). Сжатие (`CompressionLayer`) — только на `/api/sync/*`.

## Авторизация

Один статический токен (`NIMBUS_API_TOKEN`), сравнение за постоянное время. Источники: `Authorization: Bearer`,
cookie `nimbus_token` (HttpOnly, SameSite=Lax; значение — hex токена), для WebSocket также `?token=`.
`/api/health`, `/api/auth/login` и `/api/auth/session` открыты. Внутренний `/api/internal/raw/…` (для ffmpeg) требует секрет процесса в заголовке `X-Nimbus-Internal` (32 случайных байта, создаются при старте, не логируются) и loopback; в OpenAPI его нет. Стрим рвётся, если молчит дольше `stream_idle_timeout` (45 с; 120 с для `?download=1`) — плеер переподключается с `Range`.
Веб-сервер (`proxy.ts`) перенаправляет на `/login` без валидной cookie и ходит в API с токеном из своего окружения.
