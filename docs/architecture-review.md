# Ревью архитектуры Nimbus (2026-11-13)

Ревью сделано по коду на коммите `b0482b8` (план `PLAN.md`, шаги 01–23 выполнены). Документ фиксирует,
что есть, что не так и какой шаг `ROADMAP.md` это исправляет. Номера в скобках — шаги дорожной карты.

## 1. Итог в двух абзацах

**Бэкенд** устроен разумно: крейты разделены по ответственности, внешние сервисы в тестах подменяются
(wiremock, локальный рой librqbit), очередь задач на Postgres с `SKIP LOCKED` и дедупликацией, ~290 тестов.
До «rock solid» не хватает трёх вещей: (а) надёжности очереди и торрент-движка в краевых случаях
(зависшие задачи, глобальная блокировка движка, незавершаемые альбомы); (б) скорости — конвейер
искусственно растянут паузами и низким параллелизмом, метаданные торрента добываются из сети дважды;
(в) измеримости — покрытие не измеряется и не контролируется в CI.

**Фронтенд** — Next.js 16 canary с Server Components, `'use cache'`, Server Functions и экспериментальными
флагами. Каждая навигация и каждое live-событие — это поход на сервер Next (`router.refresh()`), данные на
клиенте не живут, офлайна нет, скачивания треков на устройство нет. Для приложения длительного пользования
за авторизацией SSR ничего не даёт, а стоит дорого: второй сервер, хрупкая canary-сборка, задержки на
каждом переходе. Нужна смена модели: **клиентское local-first приложение** (SPA + PWA), которое один раз
синхронизирует всю библиотеку, хранит её в IndexedDB и держит в памяти; сервер — только API.

## 2. Что сделано хорошо (сохраняем)

- Границы крейтов: `core` / `db` / `musicbrainz` / `trackers` / `matcher` / `torrent` / `library` / `worker` / `api`.
- `torrent` — единственное место, знающее про librqbit; наружу — трейты `MetadataFetcher`, `FileProvider`.
- Очередь задач: `FOR UPDATE SKIP LOCKED`, `dedup_key`, `LISTEN/NOTIFY` + опрос, backoff, изоляция паник.
- Тесты провайдеров на фикстурах, matcher на сценариях, `tests/swarm.rs` с настоящим локальным роем.
- OpenAPI генерируется из кода, типы фронтенда — из OpenAPI, CI проверяет расхождение.
- Чистая логика плеера (`web/providers/player/engine.ts`) отделена от DOM — переносится без изменений.
- Визуальный язык (токены Tailwind v4 в `globals.css`, карточки, плеер) — нравится, сохраняем.

## 5. Целевая архитектура

```
┌──────────────────────── Браузер / PWA ────────────────────────┐
│ React SPA (Vite, bun)                                          │
│  ├─ Store в памяти (zustand) ◄── гидратация ── IndexedDB       │
│  ├─ Sync engine: snapshot → changes(cursor) ◄─ WS «poke»       │
│  ├─ Плеер (engine.ts) ── <audio src=/api/tracks/{id}/stream>   │
│  └─ Offline: OPFS (треки, blob URL) + Service Worker (shell)   │
└───────────────┬────────────────────────────────────────────────┘
                │ REST /api/* · WS /api/ws · статика SPA
┌───────────────▼──────────── Rust (axum) ───────────────────────┐
│ api ── sync · library · stream · acquisition · settings        │
│ worker ── очередь с heartbeat/приоритетами                      │
│   import(MB пачками) → discover(провайдеры ∥) → verify(∥)      │
│   → download manager (pin) → evict                             │
│ torrent ── librqbit, per-torrent блокировки, .torrent в БД     │
└───────────────┬────────────────────────────────────────────────┘
                ▼ PostgreSQL
```

### Ключевые решения

1. **SPA вместо Next.js.** Новый клиент в `client/`: Vite + React 19 + React Router + Tailwind v4, пакетный
   менеджер и раннер — **bun**. Компоненты и токены дизайна переносятся из `web/` почти без изменений
   (они и так клиентские). `web/` удаляется на шаге 48 после паритета. Альтернатива «Next static export»
   отвергнута: динамические маршруты, Server Functions и `'use cache'` всё равно пришлось бы выкинуть,
   а canary-зависимость осталась бы.
2. **Local-first данные.** Вся библиотека (артисты, альбомы, треки, плейлисты) синхронизируется целиком:
   `GET /api/sync/snapshot`, затем `GET /api/sync/changes?cursor=`. Курсор — `xmin` снимка Postgres, строки
   помечены `txid` записавшей транзакции (триггер): дельта может прислать лишнее, но **никогда не теряет**
   изменения и не требует блокировок. WebSocket — только «poke» (подтянуть дельту) плюс мгновенные
   статусы. Экраны читают только из памяти → навигация без сети.
3. **Офлайн-треки.** Аудио хранится в OPFS и играется через объектный URL файла (перемотка работает,
   в память файл не читается); service worker аудио не перехватывает — так проще и надёжнее на iOS.
   Очередь скачивания и управление местом — на клиенте. Shell приложения — в precache service worker.
4. **Один процесс на сервере.** Бэкенд раздаёт собранный SPA (`NIMBUS_WEB_DIR`), Node и обязательный Caddy уходят.
5. **Скорость конвейера.** `.torrent` сохраняется в БД при первой же встрече (verify или провайдер) и
   используется для мгновенного старта; параллелизм метаданных/verify/discover настраивается и по умолчанию
   на порядок выше; паузы-«лесенки» заменены приоритетами очереди и лимитерами провайдеров; MB — пачками
   и с настраиваемым endpoint.
6. **Управление загрузками.** Альбом имеет вычисляемое состояние приобретения
   (`searching / missing / partial / available / downloading / downloaded`), его можно закрепить для
   скачивания на сервер; поиск не найденного повторяется автоматически и по кнопке (в том числе массово).
7. **Качество как процесс.** `docs/DEVELOPMENT.md`: цели покрытия с «храповиком» в CI, запрет `unwrap`
   в боевом коде, обязательное ревью диффа после каждого шага.

## 6. Риски

- **librqbit** — внешняя библиотека с меняющимся API; все шаги, трогающие движок, обязаны сверяться с
  исходниками установленной версии (`~/.cargo/registry/src/*/librqbit-*`).
- **OPFS / service worker на iOS Safari** — поведение отличается (вытеснение хранилища у не установленных
  PWA, ограничения фона). Шаги 45–47 содержат явные проверки и деградацию.
- **Миграция фронтенда** — самая объёмная часть. Риск снят тем, что старый `web/` работает до шага 48,
  а паритет проверяется чек-листом и e2e.
- **MusicBrainz** — публичный лимит нельзя обойти честно; заметное ускорение массового импорта без mirror
  ограничено сокращением числа запросов.
