# Шаг 35 — Закрытие покрытия бэкенда до цели, property-тесты, отказоустойчивость

**Фаза 1 · Зависит от:** 26–34 · **Закрывает находку:** Q3 · **Контрольная точка «бэкенд rock solid»**

## Зачем

Шаги 26–34 писали тесты на своё поведение. Этот шаг доводит дело до измеримого результата:
покрытие не ниже целей из `docs/DEVELOPMENT.md` §4, парсеры проверены на произвольном вводе,
а конвейер целиком переживает отказы (падение посреди задачи, недоступные внешние сервисы, рестарт).
Новой функциональности нет; найденные по дороге баги исправляются здесь же с регрессионным тестом.

## Текущее состояние

- `docs/coverage.md` (создан на шаге 25, обновлялся в Журнале) — исходное покрытие и список худших файлов.
- `backend/coverage-threshold.txt` — текущий порог храповика.
- `backend/crates/testkit` — `eventually`, общие фейки (`FakeProvider`, `FakeFetcher`, фейковый `FileProvider`, `fake_swarm`), накопленные шагами 26–33.
- Тесты: `crates/*/tests/*.rs`. Прочитай по одному файлу из каждого крейта, чтобы писать в том же стиле.

## Что сделать

1. **Измерить.** `just backend-cov-html`, затем отчёт по файлам (`cargo llvm-cov report --summary-only` после прогона или `--json`).
   Обнови `docs/coverage.md`: таблица «крейт → % строк» и список всех файлов с покрытием ниже 90 %.
2. **Проверка порогов по крейтам.** Скрипт `scripts/cov-check.sh` (bash + `jq`): принимает JSON-отчёт `cargo llvm-cov --json`,
   считает покрытие строк по путям и падает, если:
   - workspace < 90 %;
   - любой из `crates/torrent/`, `crates/worker/`, `crates/matcher/`, `crates/db/src/repo/jobs.rs`, `crates/api/src/stream.rs` < 95 %.
   Рецепт `just backend-cov` вызывает его после прогона (один прогон тестов, два использования отчёта). CI использует тот же рецепт.
3. **Закрыть пробелы.** Для каждого файла ниже цели — тесты на непокрытые ветки. Приоритет — ветки ошибок и краевые случаи,
   а не геттеры. Правила:
   - непокрытая ветка, которую невозможно вызвать, — мёртвый код: удалить, а не «покрывать»;
   - ветка «не может случиться» → `unreachable!`/`expect` с объяснением инварианта (такие строки llvm-cov не считает непокрытыми только если их нет — поэтому предпочитай перестройку кода так, чтобы ветки не было);
   - исключать файлы из отчёта нельзя (кроме уже разрешённых в `DEVELOPMENT.md` §4).
4. **Property-тесты (`proptest`, dev-зависимость workspace).** Для каждого — «не паникует на любом вводе» плюс содержательное свойство:
   | Что | Где | Свойство |
   |---|---|---|
   | Разбор заголовка `Range` | `api/src/stream.rs` | результат всегда внутри `[0, size)`, `start <= end`; валидные формы (`a-b`, `a-`, `-n`) разбираются обратно в исходные числа |
   | CUE-парсер | `matcher/src/cue.rs` | сгенерированный валидный CUE → те же треки и таймкоды; времена монотонны |
   | Имена файлов | `matcher/src/filename.rs` | для сгенерированного `NN - Title.ext` (с вариациями разделителей/регистра) номер и название извлекаются |
   | Нормализация | `matcher/src/normalize.rs` | идемпотентность: `norm(norm(x)) == norm(x)` |
   | `.torrent` (bencode) | `trackers/src/torrent_file.rs` | сгенерированный торрент → тот же info-hash и список файлов; случайные байты → `Err`, не паника |
   | Magnet | `trackers/src/magnet.rs` | построить → разобрать → тот же info-hash |
   | Экранирование Lucene | `musicbrainz/src/lucene.rs` | в результате нет неэкранированных спецсимволов |
   | Курсоры | постраничные (`library.rs`, `acquisition`) и `sync` | encode → decode — тождество; мусор → 400, не 500 |
   | Ранжирование | `trackers/src/rank.rs` | порядок не зависит от порядка входа (стабильность), оценки конечны |
   Число случаев по умолчанию (256); файлы регрессий `proptest-regressions/` коммитятся.
5. **Сквозной тест конвейера** `crates/api/tests/pipeline.rs` (Postgres + фейковые MB/провайдеры + локальный рой):
   добавить артиста → импорт → поиск → проверка → треки `found` → закрепить альбом → файлы скачаны → треки `ready` →
   стрим отдаёт байты, совпадающие с исходными → `GET /api/sync/changes` показывает итоговые статусы.
6. **Тесты на отказы** (тот же стенд, файл `crates/api/tests/chaos.rs`):
   - **рестарт посередине:** остановить пул воркеров (отмена токена) в момент, когда задачи `running`; создать новый пул на той же БД → конвейер доходит до конца, дублей `track_sources`/`album_torrents` нет, ни один трек не остался в `adding`;
   - **провайдер лежит:** один фейковый провайдер всегда отвечает ошибкой/таймаутом → альбом находится через второй, предохранитель открыт, общее время не растёт линейно от числа альбомов;
   - **MusicBrainz отвечает 503 через раз** → импорт завершается, прогресс не теряется;
   - **все пиры пропали во время загрузки** → закрепление уходит в `failed("stalled")` или переключается на другой источник; стрим завершается ошибкой по таймауту простоя, а не висит;
   - **исчерпание попыток** у `verify_torrent` и `discover_album` → треки получают `not_found` с причиной, альбом не остаётся в `adding`;
   - **двойная доставка:** одну и ту же задачу выполнить дважды подряд (каждый вид задачи) → состояние БД идентично однократному выполнению.
7. **Проверка авторизации по OpenAPI.** Тест, который берёт спецификацию из `ApiDoc::openapi()`, перебирает **все** пути и методы,
   подставляет в параметры пути `1`, шлёт запрос без токена при включённой авторизации и ожидает 401 — для всех, кроме явного списка публичных
   (`/api/health`, `/api/openapi.json`, `/api/auth/*`, `/api/ws`). Новый эндпоинт без авторизации больше не пройдёт незамеченным.
8. **Устойчивость тестов.** Прогнать `cargo test --workspace` 5 раз подряд (и один раз с `--test-threads=1`). Любой нестабильный тест —
   починить причину (гонка, порт, время), а не добавлять повтор.
9. **Порог.** Записать в `coverage-threshold.txt` `floor(текущее) − 1` (должно получиться ≥ 89). Обновить `docs/coverage.md`.

## Критерии приёмки

```
just db-up && just check && just test
just cov                      # проходит: workspace ≥ 90 %, ключевые крейты ≥ 95 %
for i in 1 2 3 4 5; do (cd backend && cargo test --workspace -q) || break; done
```

В Журнал: итоговая таблица покрытия по крейтам, число тестов, время полного прогона, список исправленных багов.

## Не входит в шаг

- Нагрузочные измерения на больших данных (шаг 50).
- Тесты на живые внешние сервисы (остаются `#[ignore]`).

## Подводные камни

- Не гонись за процентом через тесты, которые ничего не утверждают. Каждый тест должен падать при поломке поведения — проверь это на 2–3 новых тестах, временно сломав код.
- Тесты роя под инструментированием медленнее; если полный `just cov` идёт дольше 15 минут — ищи тесты с реальными ожиданиями (`sleep`, длинные таймауты) и переводи на `tokio::time::pause` или уменьшай настраиваемые таймауты в тестовой конфигурации.
- Если цель 95 % для какого-то крейта недостижима без нечестных приёмов — остановись, оставь шаг `[~]`, опиши в Журнале конкретные строки и причину. Понижать цель молча нельзя.
- `proptest` с сетью/БД не совмещай: property-тесты — только для чистых функций.
