# Шаг 49 — Аудит интерфейса: все экраны, темы, размеры, доступность, производительность

**Фаза 3 · Зависит от:** 48

## Зачем

Требование — «приложение выглядит как настоящее, дизайн везде сделан хорошо». Экраны писались
разными шагами; этот шаг смотрит на приложение целиком глазами пользователя: каждый экран, в каждой
теме, на телефоне и на большом мониторе, с клавиатуры, с длинными строками, с пустыми и огромными
данными — и исправляет всё, что выбивается. Плюс измеримые бюджеты производительности, закреплённые тестами.

## Текущее состояние

- Все экраны `client/src/screens/**`, примитивы `client/src/components/ui/**`, галерея `/dev/ui` (шаг 43).
- Мок-бэкенд с заливкой больших данных (`/__test/seed`), e2e-инфраструктура.
- Правила: `docs/DEVELOPMENT.md` §5 («Дизайн», «Доступность»).

## Что сделать

1. **Матрица скриншотов.** Playwright-сценарий `client/tests/audit/screens.spec.ts` (отдельный проект конфигурации, не входит в обычный `test:e2e`; рецепт `just client-audit`):
   - экраны: вход; главная (пустая / обычная); библиотека (каждая вкладка); артист (обычный / импортируется / импорт упал); альбом (все треки готовы / частично найден / ищется / не найден); плейлист; избранное; поиск (пусто / результаты / ошибка / офлайн); источники альбома; диалог источника трека; диалог «в плейлист»; командная палитра; настройки (каждый раздел); загрузки (каждая вкладка, пустые и заполненные); полноэкранный плеер; очередь; 404; экран ошибки; первая синхронизация; офлайн-состояния;
   - для каждого: светлая и тёмная тема × ширины 360, 768, 1440;
   - дополнительно: язык `de` и `ja` для экранов с плотным текстом (настройки, загрузки) на 360;
   - результат: `client/test-results/audit/<экран>-<тема>-<ширина>.png` (в git не коммитится).
2. **Просмотр и исправление.** Просмотри **каждый** скриншот (инструмент чтения изображений) по чек-листу и исправляй код:
   - сетка и отступы: единый шаг (4/8 px), одинаковые поля страниц, выравнивание заголовков и содержимого по одной линии на всех экранах;
   - типографика: одна шкала размеров, заголовки страниц одного уровня выглядят одинаково; нет обрезанного или наезжающего текста; длинные названия — многоточие или `Marquee` там, где он уже принят;
   - элементы управления: одинаковая высота и скругления, кнопки одного смысла — одного вида на всех экранах, иконки одного размера и толщины линий;
   - цвета — только токены; контраст текста ≥ 4.5:1 (в т. ч. `text-muted` на `card` в обеих темах); состояние `disabled` различимо;
   - пустые состояния, загрузка (skeleton повторяет форму содержимого, нет сдвига вёрстки при появлении данных), ошибки — единый стиль;
   - мобильная вёрстка: область нажатия ≥ 44 px, ничего не перекрыто мини-плеером и панелью вкладок, безопасные зоны, нет горизонтальной прокрутки страницы;
   - большие экраны: содержимое не растягивается бесконечно (разумная максимальная ширина текстовых колонок, сетка карточек добавляет колонки).
   Список найденного и исправленного — в Журнал (кратко, по экранам).
3. **Доступность.** `@axe-core/playwright` на каждом экране матрицы (одна тема, 1440): нарушений уровня `serious`/`critical` — ноль (исключения — только с комментарием-обоснованием).
   Проход с клавиатуры (тест): Tab-порядок логичен, видимый фокус везде, диалоги ловят фокус и возвращают его, Esc закрывает верхний слой, меню управляются стрелками, все действия со строкой трека доступны без мыши.
   `prefers-reduced-motion`: переходы и бегущие строки выключены (тест на отсутствие анимаций у ключевых элементов).
4. **Бюджеты производительности** — тесты в `client/tests/perf/` (отдельный проект Playwright, рецепт `just client-perf`, подключить в CI) с заливкой 5 000 альбомов / 60 000 треков (пороги с запасом ×3 для CI; фактические цифры — в Журнал):
   | Метрика | Цель | Порог в тесте |
   |---|---|---|
   | Переход между любыми двумя основными экранами (клик → содержимое) | < 50 мс | 150 мс |
   | Холодный старт с данными в IndexedDB (навигация → содержимое главной) | < 1.5 с | 4 с |
   | Прокрутка списка 60 000 треков: кадры длиннее 50 мс за 3 с прокрутки | 0 | ≤ 3 |
   | Ввод в поле поиска: задержка до локальных результатов | < 50 мс | 150 мс |
   | Применение дельты из 100 изменений при открытом списке треков | без видимого подвисания | самая длинная задача < 100 мс |
   | Память после 50 переходов между экранами | не растёт | прирост кучи < 20 % после принудительной сборки мусора (CDP) |
   Нарушение цели — профилировать (React Profiler, Performance) и исправлять причину: лишние подписки на store, немемоизированные селекторы, отсутствие виртуализации, тяжёлые эффекты.
5. **Размер сборки.** Скрипт `client/scripts/check-bundle.ts` (bun): начальный JS (то, что грузится до первого экрана) ≤ 350 КБ gzip, CSS ≤ 40 КБ gzip; пороги — в файле `client/bundle-budget.json`, храповик как у покрытия (после шага записать фактическое + 5 %). Подключить в `just client-build` и CI.
   Превышение — искать по отчёту (`vite-bundle-visualizer`/`rollup-plugin-visualizer`): дубли зависимостей, импорт всей библиотеки иконок, словари не в отдельных чанках.
6. **Полнота i18n.** Тест: во всех 14 словарях один набор ключей (есть с шага 36), **нет неиспользуемых ключей** (статический поиск `t('…')` по `src/`), нет ключей, значение которых совпадает с английским в неанглийском словаре, кроме списка разрешённых (названия, «OK»). Найденные непереведённые строки — перевести.
   Поиск «зашитых» строк: `grep` кириллицы и английских фраз в JSX вне словарей — исправить.
7. **Мелочи «настоящего приложения».** Проверь и доведи: заголовок вкладки на каждом экране; `theme-color` меняется с темой; фавикон и иконки PWA; выделение текста выключено на элементах управления и включено на тексте; контекстное меню и долгое нажатие на мобильных не вызывают системных меню на обложках/кнопках;
   нет «прыжка» вёрстки при появлении панели плеера; состояние прокрутки и вкладок переживает «назад»; двойной клик не выделяет текст в списках; фокус не теряется после закрытия диалогов; toast не перекрывает плеер на мобильных.
8. **Безопасная чистка.** Удалить неиспользуемые компоненты/стили/зависимости (проверка: `bunx knip` или аналог — разово, без добавления в зависимости, если не хочется; результат в Журнал), маршрут `/dev/ui` не попадает в продакшен-сборку.
9. **Реальные устройства.** Если в среде доступен WebKit Playwright — прогнать матрицу п. 1 (360 и 768) и e2e плеера/офлайна в WebKit, исправить расхождения.
   В Журнал — явный список того, что **не** удалось проверить автоматически и требует ручной проверки на iPhone/Android (установка на домашний экран, фоновое воспроизведение, экран блокировки, офлайн после перезапуска приложения).

- клавиатурные сценарии (п. 3); reduced motion;
- все тесты бюджетов (п. 4) и размера сборки (п. 5);
- тесты i18n (п. 6);

## Не входит в шаг

- Новые функции и изменение принятого визуального языка (цвета, шрифты, форма карточек) — он нравится и сохраняется; шаг добивается единообразия.
- Сравнение скриншотов с эталонами в CI (нестабильно между платформами): скриншоты — инструмент аудита, а не тест.

## Подводные камни

- Скриншотов получится несколько сотен. Смотри их по экранам (все варианты одного экрана подряд), а не по порядку файлов; исправив общий компонент, пересними и пересмотри все экраны, где он используется.
- Тесты производительности в CI шумные: измеряй медиану из 5 повторов, а не одно значение; пороги с запасом уже заложены — не поднимай их, если тест «иногда падает», ищи причину.
- Правка общего примитива ради одного экрана ломает другие — после каждого изменения в `components/ui` перегенерируй скриншоты галереи `/dev/ui`.
- Не «чини» контраст изменением токенов без проверки всех мест, где токен используется.
