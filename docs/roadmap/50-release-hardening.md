# Шаг 50 — Финал: сквозные сценарии, нагрузка, документация

**Фаза 3 · Зависит от:** 35, 49

## Зачем

Последняя проверка того, что цели дорожной карты достигнуты **вместе**, на собранном продукте: полный
стек под нагрузкой большой библиотеки, отказы и рестарты, длительная работа. Плюс приведение
документации в состояние «новый человек (или модель) разберётся за 15 минут».

## Текущее состояние

- Один образ `nimbus` + Postgres (шаг 48); `just e2e` — сквозной сценарий на фейковых внешних сервисах (`NIMBUS_FAKE_EXTERNAL`, feature `test-fakes`).
- Тесты бэкенда: `pipeline.rs`, `chaos.rs` (шаг 35); клиент: unit, e2e, аудит, бюджеты (шаг 49).
- Пороги: `backend/coverage-threshold.txt`, `scripts/cov-check.sh`, `client/vitest.config.ts`, `client/bundle-budget.json`.
- `ROADMAP.md` — цели 1–6 и Журнал всех шагов (в нём — записи «Замечено» и ручные проверки, отложенные на потом).

## Что сделать

1. **Разбор Журнала.** Прочитай **весь** Журнал `ROADMAP.md`. Выпиши все пункты «Замечено», «Отклонения», `БЛОК` и отложенные ручные проверки.
   Для каждого: исправить сейчас (если это дефект или небольшая доработка) / вынести в `docs/backlog.md` с обоснованием. Ничего не должно остаться «висящим» только в Журнале.
2. **Генератор нагрузки для фейковых сервисов.** В режиме `NIMBUS_FAKE_EXTERNAL` (модуль `fakes`) добавить управляемый размер каталога: переменные `NIMBUS_FAKE_ARTISTS`, `NIMBUS_FAKE_ALBUMS_PER_ARTIST`, `NIMBUS_FAKE_TRACKS_PER_ALBUM`,
   задержки ответов (`NIMBUS_FAKE_LATENCY_MS`) и долю отказов (`NIMBUS_FAKE_FAILURE_RATE`) — детерминированно (seed). Фейковый рой раздаёт маленькие файлы.
3. **Нагрузочный сценарий** `scripts/load.sh` + `client/tests/stack/load.spec.ts` (запуск `just load`, не входит в CI по умолчанию — отдельный workflow с ручным запуском):
   - библиотека: 300 артистов × ~15 альбомов × ~12 треков (≈ 54 000 треков) добавляется через API;
   - измерить и записать: время импорта всего каталога; время до первого найденного альбома после добавления артиста; пропускная способность очереди (задач/мин по видам); пиковое число соединений с БД и отсутствие ошибок пула;
     время и размер `GET /api/sync/snapshot`; время дельты после изменения 1 / 1 000 строк; потребление памяти процессом бэкенда в покое и на пике; время холодного старта клиента с этой библиотекой и переходов между экранами (метрики шага 49 на реальном бэкенде);
   - цели (если не достигнуты — профилировать и исправлять, это часть шага):
     | Метрика | Цель |
     |---|---|
     | Первый альбом артиста начал искаться после добавления | < 5 с (без учёта задержки фейкового MB) |
     | Очередь не простаивает: при наличии задач занято ≥ 80 % воркеров каждого вида | да |
     | Снимок 54 000 треков | < 3 с, < 5 МБ в gzip |
     | Дельта после одного изменения | < 100 мс |
     | Ошибок `pool timed out`, зависших задач (`running` без heartbeat), треков в `adding` после завершения очереди | 0 |
     | Память бэкенда на пике | записать; рост после завершения нагрузки не продолжается |
4. **Отказы на полном стеке** (`client/tests/stack/resilience.spec.ts`, управляет контейнерами через `docker compose`):
   - `docker compose restart nimbus` во время импорта артиста и во время закреплённой загрузки альбома → после рестарта всё доходит до конца; клиент сам переподключается, показывает «нет связи» и возвращается без перезагрузки страницы; музыка, игравшая из офлайн-файла, не прерывается;
   - `docker compose stop db` на 20 с и запуск → бэкенд не падает, отвечает 503 на API, после возвращения БД очередь продолжает работу;
   - остановка `nimbus` на минуту при открытом клиенте → клиент работает с локальными данными, после запуска синхронизируется дельтой (не снимком);
   - `NIMBUS_FAKE_FAILURE_RATE=0.3` → каталог из 20 артистов всё равно полностью обрабатывается (повторы), итоговые состояния корректны.
5. **Длительный прогон (soak).** `just soak` (30 минут, вручную): клиент в headless-браузере непрерывно воспроизводит плейлист и ходит по экранам, сервер параллельно импортирует артистов.
   Критерии: воспроизведение не прерывалось (нет пауз > 2 с, кроме смены трека), память вкладки и процесса бэкенда не растёт монотонно (сравнить 10-ю и 30-ю минуты, допуск 15 %), в логах бэкенда нет `ERROR`/паник, число открытых файлов и задач tokio стабильно.
6. **Итоговая проверка целей.** Таблица в Журнале — цель из `ROADMAP.md` → доказательство:
   - цель 1: покрытие по крейтам (вывод `just cov`), число тестов, результаты п. 4;
   - цель 2: цифры п. 3 против тех же цифр до шагов 26–30 (из Журнала шага 25/29/30, если записаны; иначе — только текущие);
   - цель 3: сценарий «не найден → повтор → найден → скачан на сервер» в стековом e2e;
   - цель 4: метрики навигации и холодного старта, офлайн-сценарий;
   - цель 5: результаты аудита шага 49;
   - цель 6: в репозитории нет `pnpm`/`npm`-lock-файлов, сборка образа использует bun.
   Цель не подтверждена → шаг остаётся `[~]`, в Журнале — что именно не достигнуто.
7. **Финальные пороги.** Убедиться, что храповики стоят на фактических значениях: `coverage-threshold.txt`, пороги Vitest, `bundle-budget.json`.
8. **Документация** (переписать по факту, а не дополнять):
   - `README.md` — что это, скриншоты (4 штуки из аудита: главная, альбом, загрузки, настройки — положить в `docs/img/`), быстрый старт, настройка источников, офлайн и установка на телефон, своё зеркало MusicBrainz, обновление, резервное копирование (том БД + `data/`), устранение неполадок (нет пиров, MB отвечает 503, не находится альбом → экран «Загрузки»);
   - `docs/architecture.md` — актуальная схема, крейты, конвейер, модель синхронизации, офлайн-хранилище, жизненный цикл задач и торрентов;
   - `docs/api.md` — сверить с OpenAPI (каждый эндпоинт упомянут); события WebSocket;

## Тесты (обязательные)

- `just e2e` (стек), `resilience.spec.ts` — зелёные;
- `just load` выполнен, цели п. 3 достигнуты (цифры в Журнале);
- `just soak` выполнен (или, если среда не позволяет 30 минут, — укороченный 5-минутный прогон с пометкой в Журнале, полный — в списке ручных проверок);
- тест документации: скрипт сверяет список путей OpenAPI с `docs/api.md` и список переменных `NIMBUS_*` в коде с `docs/operations.md` и `.env.example` (расхождение — ошибка); подключить в `just check`;
- все прежние: `just check && just test && just cov && just client-e2e && just client-audit && just client-perf`.

## Критерии приёмки

```
just db-up && just check && just test && just cov
just client-build && just client-e2e && just client-perf
./scripts/build.sh && just e2e && just load
```

Если Docker недоступен в среде выполнения — выполнить всё, что возможно без него, оставить `[~]` и записать `БЛОК:` с точным списком команд, которые должен запустить человек.

## Подводные камни

- Нагрузочный сценарий на фейках проверяет **нашу** систему, а не внешние сервисы: реальные скорости MusicBrainz и торрентов ограничены снаружи — не обещай в README цифр, полученных на фейках.
- Управление контейнерами из Playwright-теста (`docker compose restart`) требует, чтобы тест запускался с хоста, а не из контейнера; длительности ожиданий — через опрос `/api/health`, без фиксированных пауз.
- Не подгоняй цели под результат: если цель не достигнута и причина не найдена за разумное время — честная запись в Журнале и пункт в бэклоге лучше, чем изменённая таблица.
- Переписывая документацию, не удаляй разделы, на которые ссылаются файлы шагов (якоря `docs/DEVELOPMENT.md` §4, §7) — шаги остаются историей, ссылки должны работать.
