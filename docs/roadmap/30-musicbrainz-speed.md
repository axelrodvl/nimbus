# Шаг 30 — MusicBrainz: пачки, burst, настраиваемый endpoint

**Фаза 1 · Зависит от:** 26, 29 · **Закрывает находки:** M1–M4 (поглощает шаг 24 старого плана)

## Зачем

Публичный MusicBrainz разрешает в среднем **1 запрос в секунду с IP** — это серверное ограничение,
«много потоков» против него дают только 503. Ускориться можно тремя способами, и шаг делает все три:

1. **меньше запросов** — получать релизы артиста пачками вместе с треклистами вместо запроса на каждый альбом;
2. **burst** — короткая очередь интерактивных запросов (поиск) проходит без ожидания;
3. **свой endpoint** — если пользователь указал зеркало MusicBrainz, лимит снимается и импорт идёт действительно параллельно.

## Текущее состояние

- `backend/crates/musicbrainz/src/limiter.rs` — «один запрос за `interval`» + приоритет интерактивных; burst нет.
- `backend/crates/musicbrainz/src/client.rs` — `MbConfig { base, min_interval: 1100 мс, retry_delay, timeout, lb_base }`; `get_json` (кэш `mb_cache` → single-flight → лимитер → HTTP с повторами на 503/429);
  `artist_release_groups` (browse по 100), `canonical_release_with_tracklist(rg)` (browse релизов группы с `inc=media recordings artist-credits`), `pick_canonical_release`, `release_tracklist`.
- `backend/crates/musicbrainz/src/canonical.rs` — `pick_canonical` (выбор каноничного релиза из кратких описаний).
- `backend/crates/library/src/service.rs` — `import_artist_skipping`: на каждую release group вызывает `ensure_album` → `canonical_release_with_tracklist`.
- `backend/crates/api/src/main.rs` — `MbClient` создаётся из env один раз; настройки MB в `Settings` отсутствуют.
- Фикстуры: `backend/crates/musicbrainz/tests/fixtures/*.json` (в т.ч. `real_releases_browse.json`); тесты — `tests/client.rs` (29 тестов).
- Документация MB API: https://musicbrainz.org/doc/MusicBrainz_API (browse, `inc`, лимиты) — **сверь ограничения `limit` для browse релизов с `inc=recordings`** (если сеть доступна; если нет — см. «Подводные камни»).

## Что сделать

1. **Настройки.** В `Settings` раздел
   `musicbrainz { base_url: String = "https://musicbrainz.org/ws/2/", rate_per_sec: f64 = 1.0, burst: u8 = 3, max_concurrent: u8 = 2 }`.
   Валидация: URL http/https, оканчивается на `/`; `rate_per_sec` 0 (без лимита) или `0.1..=100`; `burst` `1..=20`; `max_concurrent` `1..=32`.
   Если `base_url` — не `musicbrainz.org` и пользователь не задавал остальные поля, применяются значения для зеркала: без лимита, `max_concurrent = 8` (реализуй как функцию `effective()` и покрой тестом).
   Изменение настроек применяется на лету: `MbClient::reconfigure(&MusicbrainzSettings)` (заменяет лимитер и базовый URL; HTTP-клиент тот же) — вызывается из `api::settings::apply_settings`.
2. **Лимитер: token bucket + параллелизм.** Переписать `Limiter`:
   - ведро на `burst` токенов, пополнение `rate_per_sec` в секунду; `rate = 0` → без ограничения темпа;
   - семафор `max_concurrent` на число одновременных HTTP-запросов (guard держится до конца запроса);
   - приоритет: фоновый запрос не берёт токен, пока ждёт хотя бы один интерактивный (как сейчас), и никогда не забирает **последний** токен ведра (резерв под интерактив);
   - **адаптация:** на каждый 503/429 эффективный темп умножается на 0.5 (не ниже 0.2 req/s) и ведро опустошается; каждые 30 успешных запросов — ×1.25 до заданного `rate_per_sec`. Уважать `Retry-After`.
   Реализация без busy-loop (сейчас фоновый запрос опрашивает каждые 10 мс — заменить на `Notify`).
3. **Пакетный импорт дискографии.** Новый метод клиента:
   ```rust
   /// Все официальные релизы артиста указанных типов вместе с треклистами, сгруппированные по release group.
   pub async fn artist_releases_bulk(&self, artist: Uuid, types: &[&str]) -> Result<Vec<BulkGroup>>;
   pub struct BulkGroup { pub group: ReleaseGroupHit, pub release: Uuid, pub tracklist: ReleaseTracklist }
   ```
   Реализация: browse `release?artist={mbid}&status=official&type=album|ep&inc=release-groups+media+recordings+artist-credits&limit=N&offset=…`
   до исчерпания `release-count`; группировка по `release-group.id`; для каждой группы — `pick_canonical` среди её релизов
   (та же функция, что и сейчас → тот же выбор); треклист берётся из выбранного релиза, если он полон (`tracks.len() == track-count` на каждом носителе).
   Группы, для которых полный треклист не получен, добираются существующим `canonical_release_with_tracklist` — параллельно, `buffer_unordered(max_concurrent)`.
   Если browse вернул ошибку формата/неподдерживаемый `inc` — весь метод откатывается на старый путь (release groups + по запросу на группу), тоже параллельно.
4. **Импорт использует пачки.** `LibraryService::import_artist_skipping`: получить `artist_releases_bulk`, затем
   для каждой группы — запись альбома и треков в БД (новая `ensure_album_from(group, release, tracklist)`, без сети)
   и постановка `DiscoverAlbum` (контракт шага 29: сразу после записи альбома). Фильтры (типы, чужой артист) и
   журнал прогресса (`ImportProgress`) сохраняются; сообщение о темпе MB в журнале — актуализировать.
   Правило «релизы без пригодного треклиста пропускаются» сохраняется.
5. **Stale-if-error.** `mb_cache::get` получает режим «вернуть и просроченное»: при `RateLimited`/`Transport`/5xx
   клиент отдаёт просроченную запись (лог `warn`), если она есть. Просроченные записи удаляются фоновым
   обслуживанием не раньше чем через 30 дней после истечения (сейчас — проверь, как чистится `mb_cache`, и приведи к этому).
6. **Интерактивный поиск.** `api/src/search.rs` уже делает три запроса через `tokio::join!` — с burst 3 они
   уходят одновременно. Убедись тестом, что поиск на «тёплом» ведре не ждёт интервал.
7. **Запуск.** `main.rs`: `MbClient` создаётся из `settings.musicbrainz` (env `NIMBUS_MB_USER_AGENT` остаётся источником User-Agent).
   Режим фейков (`NIMBUS_FAKE_EXTERNAL`) переопределяет `base_url` и снимает лимит, как сейчас.
8. **Документация:** `README.md` — раздел «Своё зеркало MusicBrainz» (ссылка на `musicbrainz-docker`, какие поля настроек указать); `docs/architecture.md`.

## Тесты (обязательные; `wiremock`, время — `tokio::time::pause`)

Лимитер (unit):
- burst: первые `burst` запросов проходят без ожидания, следующий ждёт `1/rate`;
- `rate = 0` → без ожидания; `max_concurrent` ограничивает одновременные запросы;
- интерактивный обгоняет ожидающие фоновые; фоновый не берёт последний токен;
- адаптация: 503 → темп падает вдвое, ведро пустое; после 30 успехов растёт; не превышает заданный;
- нет busy-loop: при паузе времени фоновый запрос не просыпается без события (проверка через счётчик пробуждений или отсутствие прогресса виртуального времени).

Клиент:
- `artist_releases_bulk`: одна страница; несколько страниц; группа с неполным треклистом → добор по группе; ответ неподдерживаемого формата → откат на старый путь; результат выбора каноничного релиза **совпадает** с `canonical_release_with_tracklist` на тех же данных (тест-эквивалентность на фикстурах);
- число HTTP-запросов для артиста с 12 группами: старый путь ≥ 13, пакетный ≤ 3 (assert по счётчику wiremock);
- stale-if-error: просроченная запись отдаётся при 503 и при сетевой ошибке; свежая сеть обновляет запись;
- `reconfigure` меняет базовый URL и лимит без пересоздания клиента; запросы в полёте завершаются.

Импорт (`crates/library` / `crates/api/tests/library.rs`): импорт артиста через пачки создаёт те же альбомы/треки, что и раньше (существующие тесты импорта проходят); фильтры типов и «чужой артист» работают; прогресс пишется.
Настройки (`crates/api/tests/settings.rs`): валидация раздела; `effective()` для зеркала; применение на лету (следующий запрос идёт на новый URL).

**Фикстура пакетного ответа:** если есть сеть — запиши реальный ответ для артиста с 2–3 альбомами в
`tests/fixtures/real_releases_by_artist.json` (тест на живой сервис — `#[ignore]`); если нет — собери из
существующих `real_releases_browse.json`/`real_release.json`, сохранив структуру browse-ответа (`release-count`, `releases[]` с `release-group`, `media[].tracks[]`).

**Измерение (в Журнал):** число запросов и виртуальное время импорта артиста с 30 альбомами: до / после (публичный лимит) / после с `rate = 0, max_concurrent = 8`.

## Подводные камни

- Browse релизов с `inc=recordings` может иметь **меньший максимальный `limit`** (в документации MB для тяжёлых `inc` указан предел 25): не полагайся на 100 — бери `limit` из константы, определи фактический предел по документации/ответу (`releases.len()` < запрошенного при `release-count` > offset) и корректно листай по `offset += получено`.
- Один и тот же релиз может прийти дважды на границе страниц — дедуплицируй по `id`.
- Сборники и релизы «Various Artists»: browse по артисту вернёт релизы, где он — основной исполнитель релиза; фильтр «группа принадлежит другому артисту» из текущего импорта должен остаться.
- Адаптивный темп — состояние процесса; не пиши его в настройки.
- Не увеличивай значения по умолчанию для `musicbrainz.org` выше 1 req/s: это нарушение правил сервиса и путь к бану по IP/User-Agent.
