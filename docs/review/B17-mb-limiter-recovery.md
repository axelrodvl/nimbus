# B17 — После серии 503 от MusicBrainz темп запросов восстанавливается десятки минут

**Приоритет:** P2 · **Область:** `backend/crates/musicbrainz` (`limiter.rs`, `client.rs`) · **Зависит от:** —

## Проблема

Найдено при выполнении B14 (хаос-тест: «MusicBrainz недоступен дольше лимита попыток импорта»). Адаптивный
лимитер на каждый ответ 503/429 делит темп пополам до пола `MIN_ADAPTIVE_RATE` = 0,2 запроса/с и возвращает его
шагами ×1,25 **только по числу успешных запросов** — раз в `RECOVERY_EVERY` = 30 успехов:

- публичный сервер (потолок 1 запрос/с): после короткого сбоя (пять ответов 503 подряд — это один неудачный импорт
  с повторами) темп 0,2/с; до потолка — 8 шагов × 30 успешных запросов ≈ 240 запросов, из них первые 30 идут
  2,5 минуты, всего около 10–12 минут ползком уже после того, как сервер ожил;
- свой сервер без лимита (`rate_per_sec = 0`): снижение начинается с `UNLIMITED_FALLBACK_RATE` = 4/с и доходит до
  тех же 0,2/с — зеркало, отвечавшее 503 минуту (перезапуск), потом обслуживается в 20 раз медленнее, чем может.

Импорт артиста — это 2–5 запросов; при темпе 0,2/с добавление десяти артистов после сбоя занимает минуты вместо
секунд, а «30 успехов» набираются тем медленнее, чем меньше запросов делает пользователь. Пауза `Retry-After`
(`blocked_until`) при этом уже соблюдается отдельно — замедление сверх неё ничего не даёт серверу.

## Текущее состояние (прочитай перед началом)

- `backend/crates/musicbrainz/src/limiter.rs` — `on_throttled`, `on_success`, `MIN_ADAPTIVE_RATE`,
  `RECOVERY_EVERY`, `UNLIMITED_FALLBACK_RATE`, тесты в конце файла (`unlimited_rate_degrades_and_returns_to_unlimited` и соседние).
- `backend/crates/musicbrainz/src/client.rs` — обработка 503/429 (`limiter.on_throttled(Some(wait))`).

## Что сделать

1. **Восстановление по времени.** В состоянии лимитера хранить момент последнего 503/429 (`last_throttled`).
   При выдаче разрешения (там, где пополняется «ведро»): если с `last_throttled` прошло не меньше
   `RECOVERY_QUIET` = 60 с — темп ×2 (не выше потолка; для режима без лимита — возврат к «без ограничения» после
   превышения `UNLIMITED_FALLBACK_RATE`), и отсчёт начинается заново. Так после минуты без отказов темп удваивается
   каждую минуту: 0,2 → 0,4 → 0,8 → потолок за 3 минуты независимо от числа запросов.
2. Восстановление по успехам (`RECOVERY_EVERY`) оставить — оно быстрее при плотном потоке запросов.
3. Пол снижения не менять; `blocked_until` (явная пауза сервера) не трогать.
4. Время — через `tokio::time::Instant` (как сейчас), чтобы тесты шли на `tokio::time::pause()`.

## Тесты (обязательные)

В `limiter.rs` (`#[tokio::test(start_paused = true)]`):

- `rate_recovers_by_time_without_requests`: пять `on_throttled` → темп на полу; `advance(60 с)` и одно разрешение →
  темп удвоился; ещё три минуты → темп равен потолку.
- `a_new_throttle_restarts_the_quiet_period`: `on_throttled` через 50 с после предыдущего — удвоения на 60-й секунде нет.
- `unlimited_rate_returns_to_unlimited_by_time`.
- Существующие тесты восстановления по успехам остаются зелёными.
