# S12 — Фото артистов и обложки: клиент не знает, есть ли картинка, и грузит всё в момент показа

**Приоритет:** P2 · **Область:** `backend/crates/api/src/artist_image.rs`, синхронизация артистов,
`client/src/components/library/artist-avatar.tsx`, `client/src/sw/`, `client/src/lib/library/cover.ts` ·
**Зависит от:** S11 (оба меняют формат синхронизации — один подъём `SYNC_SCHEMA`, если делаются подряд; иначе свой)

## Проблема

Цель — чтобы экраны библиотеки показывали картинки с первого кадра, как уже показывают метаданные.

1. **Неизвестно, есть ли фото у артиста.** `ArtistAvatar` всегда запрашивает `/api/artist-image/{mbid}`. Для
   артиста без фото ответ — 404; service worker кэширует только удачные ответы (`cacheFirst` → `isCacheable`), так
   что **каждое** монтирование такого аватара — сетевой запрос, а инициалы проявляются с задержкой
   (`delayed-appear`) поверх пустого круга. Первый запрос по артисту синхронно ищет фото во внешних источниках
   (Wikidata/Commons, затем Deezer) — секунды.
2. **Ничего не прогревается заранее.** Обложки (`/api/covers/{kind}/{mbid}/{size}`) и фото кэшируются SW
   (`nimbus-images-v3`, cache-first, сервер отдаёт `immutable`), но только после первого показа: впервые открытый
   экран — плашки, которые заполняются по мере загрузки; офлайн — пустые плашки для всего, что не открывалось.
3. `markImageShown` / `imageLoading` помнят показанное только в памяти сессии (5000 адресов): после перезапуска
   картинки из кэша SW снова идут `lazy`/`async` — на кадр-другой пустая плашка.

## Что сделать

1. **Признак фото в синхронизации.** Колонка `artists.image` (`'yes' | 'no' | NULL` = ещё не искали) — пишется
   там, где сейчас пишется `mb_cache` `artist_image:{mbid}` (запись штампует `sync_txid` обычным триггером). Поле
   `image` в `SyncArtist`. Поиск фото — в фоне при импорте артиста в библиотеку (низкий приоритет, через
   существующую очередь задач или после импорта), а не только по первому запросу из браузера. Истечение `MISS_TTL`
   → `NULL` и повторный фоновый поиск. OpenAPI, `docs/api.md`.
2. **`ArtistAvatar`:** `image = 'no'` — инициалы сразу, без запроса и без задержки; `'yes'` — как сейчас;
   `NULL` — как сейчас (запрос; ответ обновит строку дельтой).
3. **SW:** кэшировать 404 `no_image` фото артиста на короткий срок (например, сутки, отдельная метка времени) —
   для артистов вне библиотеки (поиск, каталог), у которых нет строки в store.
4. **Прогрев миниатюр библиотеки.** Фоновый прогрев в SW-кэш обложек 250 px всех альбомов библиотеки и фото
   артистов с `image = 'yes'`: 1–2 параллельных запроса, только при `!navigator.connection?.saveData`, пауза, пока
   идёт воспроизведение со стрима или пользователь активно переходит по экранам (последняя навигация < 2 с),
   продолжение после перезапуска (что уже в кэше — пропускается по `cache.match`). Настройка в «Настройки → Хранилище»
   (по умолчанию включено), в UI — сколько прогрето. Сначала замерить и записать в Журнал объём на тестовой
   библиотеке (`just load` даёт ~54 000 треков) — если объём заметен, по умолчанию прогревать только артистов и
   последние N альбомов.
5. **Первый кадр после перезапуска:** если адрес есть в SW-кэше — `eager`/`sync`. Варианты: при старте прочитать
   ключи `nimbus-images-v3` один раз (через `caches.open` из окна — это доступно и без SW) и заполнить `shown`;
   либо хранить набор прогретых адресов вместе с прогревом. Выбрать по замеру стоимости `cache.keys()` на тысячах
   записей.

## Тесты (обязательные)

- Бэкенд: `artist_image_sets_flag_yes`, `artist_image_miss_sets_flag_no`, флаг попадает в дельту; импорт артиста
  ставит фоновый поиск фото.
- Клиент: `ArtistAvatar` с `image = 'no'` — инициалы в первом кадре, `<img>` не рендерится; с `'yes'` — `<img>`.
- SW (`client/src/sw/*.test.ts`): 404 `no_image` кэшируется и отдаётся из кэша до истечения срока; прогрев
  пропускает закэшированное, соблюдает параллельность, останавливается при `saveData` и по сигналу паузы.
- `cover.ts`: адреса из кэша после «перезапуска» идут `eager`/`sync`.
