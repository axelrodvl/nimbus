# Ревью 2026-11: фоновые задачи бэкенда и код клиента

Ревью по коду версии 0.6.1 (`c9cacb0`). Две темы:

1. **Бэкенд** — очередь задач, приоритеты, повторы, загрузки на сервер. Цель: всё, что можно довести до конца,
   доводится без участия пользователя; попытки прекращаются на время (с продолжением позже) при ошибках и
   навсегда — только когда состояние явно неисправимо (раздач нет, раздача мертва).
2. **Клиент** (`client/`) — производительность, упрощение, поддерживаемость.

Каждая задача — отдельный файл в этой папке, рассчитанный на выполнение целиком за одну сессию.
Находки получены чтением кода; тесты и замеры в рамках ревью не запускались — каждая задача начинается
с теста, который воспроизводит проблему.

## Как выполнять задачу

Запрос вида «выполни задачу `docs/review/B01-…md`». Протокол тот же, что у шагов `ROADMAP.md`:

1. Прочитай `docs/DEVELOPMENT.md` и файл задачи целиком, затем файлы из раздела «Текущее состояние»
   (код мог измениться после ревью — расхождения решай в пользу раздела «Что сделать»).
2. Сначала напиши тест, воспроизводящий проблему (он должен падать), затем исправление.
3. Прогони «Критерии приёмки», проведи ревью по `docs/DEVELOPMENT.md` §7.
4. Отметь задачу в таблице ниже (`[x]`), допиши одну строку в раздел «Журнал» этого файла
   (что сделано, что замечено), если закрыт пункт `docs/backlog.md` — убери его оттуда.
5. Коммит `review BNN: <кратко>` / `review FNN: <кратко>` (на английском). Одна задача = один коммит.

Задачи независимы, если в столбце «Зависит от» пусто. Миграции БД: бери следующий свободный номер
(`backend/migrations/0013_*.sql` и далее) — номера в файлах задач условные.

### Что проверено и признано исправным

- `claim` (`FOR UPDATE SKIP LOCKED`, порядок `priority DESC, run_after, id`), heartbeat, `requeue_stale`,
  возврат задач при остановке (`release_workers`), `Defer` для разомкнутого предохранителя.
- Повторы поиска альбома: `RETRY_DELAYS`, расписание `finish_search`, `RetryMissing` со сбросом мёртвых раздач,
  страховка `finalize_stuck_albums` для гонки двух поисков.
- Приоритеты (`INTERACTIVE > NORMAL > BACKGROUND`), наследование приоритета порождёнными задачами,
  понижение резервных `verify_torrent`. Голодание фоновых задач при постоянной обычной работе — осознанное.
- Супервизоры `Watcher` и `DownloadManager` переживают панику и ошибку БД.
- Недоступность БД: `claim`/heartbeat/запись итога логируют ошибку и продолжают; незаписанный итог возвращает
  задачу через `requeue_stale`; слушатель `NOTIFY` переподключается.
- Добавление альбома (`add_album_inner`) ставит поиск в той же транзакции; импорт артиста идемпотентен.

### Гарантия после B01–B14: у каждого состояния «в процессе» есть выход

Второй проход ревью — обход всех состояний, в которых сущность ждёт фоновой работы. Для каждого указано, кто
выводит из него сейчас и какая задача закрывает дыру. После выполнения всех задач незакрытых состояний не остаётся;
B14 превращает эту таблицу в автоматически проверяемые инварианты.

| Состояние | Штатный выход | Что могло оставить навсегда | Закрывает |
|---|---|---|---|
| Задача `queued` | воркер своего вида | все воркеры вида умерли от паники в хуке | B13 |
| Задача `running` | итог или `requeue_stale` | чужой итог поверх перехваченной задачи; crash-loop | B06, B07 |
| Задача `failed` (временная причина) | `on_exhausted` + повтор на уровне альбома | `import_artist` / `discover_artist` — повтора нет | B05 |
| Запрос на задачу, которая уже `running` | — | отброшен дедупликацией | B11 |
| Трек `adding` | `finalize` после поиска и проверок | связь или CUE без задачи; поиск не поставлен (`add_track`) | B03, B11 |
| Трек `not_found` | `RetryMissing` по `next_retry_at` | расписание стёрто или не создано | B02 |
| Раздача без метаданных | `verify_torrent`: 3 повтора → `dead` → сброс при авто-повторе | `dead` после одного таймаута (дискографии) | B01 |
| Кандидат CUE | `process_cue` | временная неудача помечена как окончательная | B12 |
| Артист в библиотеке без альбомов | `import_artist` | задача не поставлена или провалена | B05, B11 |
| Закрепление `waiting_source` | трек стал `found` → `queued` | см. «трек `not_found`» | B02 |
| Закрепление `queued` / `downloading` | `Watcher` → `ready` → `done` | нет строки `downloads`; торрент в ошибке движка | B04 |
| Закрепление `failed` | авто-повтор | лимит 5 повторов; новые источники не ищутся | B04 |
| Файл докачан | `Watcher`: `completed` + треки `ready` | второй шаг упал — треки остались `found` | B08 |
| Циклы обслуживания | — | паника завершает цикл до рестарта процесса | B13 |
| Связь или CUE-образ без задачи у альбома, где всё найдено | `requeue_lost_jobs` (раз в минуту) | страховка смотрела только на альбомы, зависшие в `adding` | B14 |
| Трек `found` при уже докачанном primary-файле | `promote_completed` (раз в минуту) | primary сменился на готовый файл — до рестарта трек не становился `ready` | B14 |
| Закрепление `dead` / постоянный отказ источника | — | повтора и поиска новых источников нет | **B15** |
| Всё отложенное после обновления версии | старые расписания (до 30 дней) | — (не дыра, а ожидание) | **B16** |

**Что остаётся остановленным намеренно** (это не дыры):

- `search.auto_retry = false` — пользователь отключил авто-повтор поиска;
- загрузки на паузе (`downloads_paused`);
- альбом без раздач / только с мёртвыми раздачами — поиск повторяется всё реже (до раза в 30 дней), но не прекращается;
- закрепление `dead` — все известные источники без сидов 6 циклов подряд; оживает при появлении нового источника
  (его ищет фоновый поиск альбома) или вручную;
- задача `failed` с `fatal = true` — сущности нет в MusicBrainz или в БД, битый CUE, неразбираемый payload.

Проверка этой таблицы автоматическая: инварианты I1–I12 (`backend/crates/db/src/repo/invariants.rs`, расшифровка —
`docs/operations.md`, «Застрявшие состояния»), хаос-тест `api/tests/convergence.rs` и сценарий (е) `just resilience`.

**Чего ревью не гарантирует:** поведение настоящих MusicBrainz, индексеров и торрент-сети (проверено только на
фейках), ошибки внутри `librqbit`, работу нескольких экземпляров бэкенда на одной БД (не поддерживается).

### Итоговая модель повторов после задач B01–B14

| Что | Временная ошибка | Когда прекращаем совсем |
|---|---|---|
| Поиск раздач альбома | повторы задачи, затем `RetryMissing` по расписанию (10 мин … сутки / 6 ч … 30 дней) | никогда: раз в 30 дней поиск повторяется |
| Метаданные раздачи | 60 с, 5 мин, 30 мин, затем `dead`; `RetryMissing` даёт новую проверку | раздача `dead` до следующего авто-повтора альбома |
| Импорт артиста, поиск дискографий | повторы задачи, затем оживление: 15 мин, 1 ч, 6 ч, далее раз в сутки | `Fatal` (артиста нет в MusicBrainz / в БД) |
| Образ с CUE | 1, 2, 5, 10, 20, 30, 30 мин, затем повтор вместе с авто-повтором альбома | битый CUE-файл |
| Загрузка на сервер | сбой запуска — 1, 5, 15 мин, далее раз в час без ограничения | все источники без сидов 6 циклов подряд (≈ 3 суток) — до появления нового источника или ручного повтора |
