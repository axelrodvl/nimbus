# F06 — Панель очереди держит в DOM всю очередь и перерисовывает её на каждой смене трека

**Приоритет:** P1 (производительность) · **Область:** `client/src/components/player/queue-panel.tsx` · **Зависит от:** —

## Проблема

«Слушать» во вкладке «Треки» (или «Слушать» у артиста или плейлиста) кладёт в очередь все треки списка: на
библиотеке из 60 000 треков в очереди оказывается 30 000. `QueuePanel` смонтирована **всегда**, даже закрытая
(`translate-x-full`, `inert`), и рисует **каждую** строку «Далее» без виртуализации:

- в DOM 30 000 `queue-row` (по ~10 элементов, `<img>` обложки, три кнопки и иконки lucide) — сотни тысяч узлов
  постоянно. Это замедляет каждый пересчёт стилей и вёрстки на любом экране, пока очередь не сменится;
- у каждой строки свои подписки: `useTrackView` (на library store) и `useCanPlay` (офлайн и связь) — 30 000
  селекторов на каждое изменение store;
- при смене трека (`index`) пересоздаётся `upcoming`, все строки получают новые колбэки и перерисовываются целиком.

Замер (ревью 2026-11-20, сборка `vite preview`, мок на 60 000 треков, Chromium без троттлинга): после «Слушать» во
вкладке «Треки» `document.querySelectorAll('[data-testid=queue-row]').length` = 30 000; за 3 с воспроизведения —
15 длинных задач по 190–330 мс (≈5 в секунду, главный поток занят больше чем наполовину; треки мока короткие, поэтому
смена трека идёт часто). CPU-профиль dev-сборки: 3,6 с из 3 с окна — синхронный рендер React (`flushSync` из
`useSyncExternalStore`), горячая функция — `QueueRow` (`queue-panel.tsx`). С очередью из альбома (12 треков) длинных
задач нет. На телефоне это заметные подвисания при каждой смене трека и медленный старт воспроизведения (монтирование
30 000 строк в цепочке клика).

## Текущее состояние (прочитай перед началом)

- `client/src/components/player/queue-panel.tsx` — `QueuePanel`, `QueueRow`.
- `client/src/components/player/player.tsx` — панель монтируется с `open={queueOpen}`.
- `client/src/components/ui/virtual-list.tsx`, `use-list-offset.ts`, `scroll-container.tsx` — виртуальный список
  поверх **общего** контейнера прокрутки оболочки (у панели свой контейнер — `div.overflow-y-auto`).
- `client/src/lib/player/queues.ts` — сколько треков попадает в очередь (`queueFromIds`, `playableQueue`).
- Тесты: `client/src/components/player/player.test.tsx`, e2e `client/tests/e2e/player.spec.ts` (очередь).

## Что сделать

1. **Закрытая панель не рисует строки.** Содержимое списка монтируется только при `open` (шапка и контейнер
   остаются — анимация выезда не ломается). Закрытие: строки снимаются после окончания `transition` (по
   `transitionend` или по таймеру `duration-200`), чтобы панель не пустела на глазах во время уезда.
2. **Виртуализация «Далее».** Строки одинаковой высоты — виртуальный список по собственному контейнеру панели.
   `VirtualList` сейчас берёт контейнер из `ScrollContainerProvider`: оберни список панели в провайдер со своим
   элементом прокрутки (или добавь `VirtualList` проп `scrollElement`). Ключ строки — `${track.id}-${i}` как сейчас.
   Текущий трек («Сейчас играет») — вне виртуального списка.
3. **Без пересборки массива.** Не строить `queue.map(...).filter(...)` на 30 000 элементов при каждом рендере:
   число строк — `queue.length - index - 1`, строка `k` — это `queue[index + 1 + k]`. Колбэки строк — по индексу,
   через стабильные функции (`player.playIndex`, `moveInQueue`), а не новые замыкания на каждую строку.
4. **Прокрутка к текущему.** При открытии панель показывает начало «Далее» (как сейчас); перестановка ↑/↓ не
   сбрасывает прокрутку.

## Тесты (обязательные)

- `player.test.tsx`: очередь из 5 000 треков — закрытая панель не содержит `queue-row`; открытая — не больше
  `видимые + overscan` строк (≤ 60); после смены трека в DOM по-прежнему ≤ 60 строк, первая строка — следующий трек.
- Перестановка ↑/↓ и удаление в виртуальном списке работают по правильным индексам (строка в середине длинной
  очереди).
- e2e `player.spec.ts`: открыть очередь длинного списка, прокрутить вниз, нажать на строку — играет она.
- Замер-сторож (vitest или `just client-perf`): «Слушать» во вкладке «Треки» на 60 000 треков — число узлов
  `queue-row` в DOM ≤ 60, за 3 с воспроизведения нет длинных задач > 100 мс (в perf-наборе — бюджетом, как другие
  пункты `budgets.spec.ts`).

## Критерии приёмки

- `just check`, `just client-test`, `just client-perf` зелёные; в Журнале — замер «до/после» (длинные задачи за 3 с
  воспроизведения с очередью из вкладки «Треки», число `queue-row` в DOM).
- Аудит (`just client-audit`) не теряет экран очереди; клавиатура и скринридер: строки доступны по Tab внутри
  открытой панели.
