# S04 — Альбом из CUE-образа «играет» первый трек и пропускает остальные

**Приоритет:** P1 · **Область:** `client/src/lib/player/controller.ts`, `backend/crates/api/src/transcode.rs` · **Зависит от:** —

## Проблема

Коммит `6a7723f` научил сервер отвечать `425 image_downloading` на трек CUE-образа, который ещё не скачан и требует
перемотки (`cue_start_ms > 0` или `?t=` > 0). Клиент знает этот код (`KNOWN_ERRORS`, `probeStreamError`), но
обрабатывает его как любую ошибку воспроизведения: `onError` → `showError(advance = true)` → через 2 с
(`ERROR_ADVANCE_MS`) — следующий трек.

Для альбома, найденного в виде образа (типичный FLAC+CUE с трекеров), это значит:

1. «Слушать альбом» из каталога: трек 1 (`cue_start_ms = 0`) играет потоком; когда он кончился, треки 2…N по очереди
   получают 425, каждый показывает ошибку 2 с и пропускается — **альбом обрывается**, хотя образ докачается через
   пару минут. Трек из середины альбома не играет вообще.
2. **Перемотка внутри трека 1** недокачанного образа — новый запрос `?t=` → 425 → ошибка → **трек пропускается**,
   хотя до перемотки он играл.
3. Статус трека — `found`, поэтому `play-remote` (S01–S03) считает его играбельным и запускает — сразу в ошибку.

Сервер при 425 на GET сам ставит образ на загрузку (`register_download`); когда образ докачан, треки образа
становятся `ready` (синхронизация).

## Текущее состояние (прочитай перед началом)

- `client/src/lib/player/controller.ts` — `onError`, `showError`, `seekTo` (ветка `transcoded`), `startCurrent`,
  `canPlayQueued`.
- `client/src/lib/player/engine.ts` — `KNOWN_ERRORS`, `probeStreamError`.
- `backend/crates/api/src/transcode.rs` — проверка `needs_seek` и 425.
- `client/src/lib/i18n/messages/*.ts` — `player.error.image_downloading`.
- Прогресс загрузки альбома: `download.progress` в `sync/engine.ts` → `LiveStore`.

## Что сделать

1. **`image_downloading` — ожидание, а не ошибка.** В контроллере: для этого кода не переходить к следующему треку.
   Статус плеера — ожидание (существующий `loading`/`buffering` или новый `waiting_download`, если без него UI
   соврёт) с текстом `player.error.image_downloading` и прогрессом загрузки альбома (`download.progress`), если он есть.
2. **Автоповтор.** Подписка на трек в store: стал `ready` → `loadAndPlay` с той же позиции (если пользователь не
   поставил паузу/не переключил трек). Плюс страховочный повтор раз в 30 с (сервер мог докачать, а событие потеряно).
3. **Перемотка в недокачанном образе.** Если `seekTo` получил 425 — вернуть воспроизведение на прежнюю позицию
   (поток с прежнего `t` ещё валиден, либо перезапрос с прежней позиции) и показать toast «Перемотка станет доступна,
   когда альбом докачается». Трек не пропускать.
4. Пользователь сам нажал «следующий» — обычный переход, ожидание снимается.

## Тесты (обязательные)

`controller.test.ts` (фейковый движок и `probe`):

- `image_downloading_does_not_advance`: `probe` → `image_downloading`; через `ERROR_ADVANCE_MS` × 2 индекс очереди не
  изменился, статус — ожидание.
- `image_downloading_resumes_when_track_ready`: затем трек в store → `ready` → `loadAndPlay` вызван с той же позиции.
- `seek_in_downloading_image_keeps_track`: играет трек, `seekTo(120)` → 425 → трек тот же, позиция возвращена, toast.
- `next_cancels_image_wait`.
- Бэкенд: существующие тесты 425 в `tests/stream.rs` зелёные (меняется только клиент, если не понадобилось иное).

## Критерии приёмки

- `just check`, `just client-test` зелёные.
- Ручная проверка на стеке (`just e2e`-фейки или живой образ): альбом из CUE — трек 1 играет, по его концу трек 2
  ждёт загрузки с понятным текстом и заигрывает сам.

## Не входит

- Ускорение загрузки образа (приоритет кусков) и нарезка без полного образа.
