# S13 — Оставшиеся запросы при открытии экранов библиотеки: статус импорта артиста и сторож на будущее

**Приоритет:** P2 · **Область:** `client/src/lib/library/use-artist-import.ts`, `client/src/screens/library/artist.tsx`,
синхронизация артистов, тесты экранов · **Зависит от:** S11, S12

## Проблема

Принцип для экранов библиотеки (главная, библиотека, артист, альбом, плейлист): **всё, что видно в первом кадре,
берётся из store**; сеть — только для действий пользователя и данных по требованию (источники трека, сведения об
аудио, каталог, поиск, экран «Загрузки»). Пользователь часто беспорядочно переходит по экранам — каждый запрос при
открытии означает скачок вёрстки (данные приходят позже кадра) и лишнюю нагрузку.

После S11 и S12 остаётся:

1. **Статус импорта дискографии на экране артиста.** `useArtistImport` (`staleTime: 0`) запрашивает
   `GET /api/artists/{id}` при открытии недавно добавленного артиста (или артиста без альбомов) — блок
   `ArtistImportStatus` появляется после ответа и сдвигает сетку альбомов. Статус живёт в таблице задач, которую
   синхронизировать целиком нельзя: задачи часто обновляются (heartbeat, прогресс).
2. **Нет сторожа.** Ничто не мешает следующему изменению снова добавить запрос в первый кадр экрана библиотеки —
   так появилась и проблема S11.

## Что сделать

1. **Грубое состояние импорта — в `SyncArtist`:** `import: 'queued' | 'importing' | 'retrying' | 'failed' | null`.
   Пишется только на **переходах** состояния задачи импорта (постановка, взятие в работу, повтор, провал,
   успех → `null`), не на heartbeat и не на прогрессе; реализация — колонка `artists.import_state`, обновляемая в тех
   же транзакциях, что и задача, или триггер на `jobs` с фильтром по типу задачи и смене `state`. Проверить, что
   heartbeat задачи импорта не даёт дельты.
2. **Экран артиста:** блок статуса рендерится из store в первом кадре. Детали (попытка, ошибка, время повтора,
   прогресс по фазам) — по-прежнему `GET /api/artists/{id}`, но запрос идёт **только** когда `import !== null`, и место
   под блок уже занято (заголовок из store, детали дорисовываются внутри без сдвига соседей).
3. **Сторож:** тест, который монтирует каждый экран библиотеки (главная, библиотека — все вкладки, артист с
   завершённым импортом, альбом, плейлист) на заполненном store с моком `fetch`, и проверяет, что в первые 100 мс не
   было ни одного запроса к `/api/*` (картинки — не `/api`, обложки/фото идут через `<img>`). Список допустимых
   исключений — явный, в тесте, с комментарием почему.
4. Записать принцип в `docs/DEVELOPMENT.md` (раздел про клиент): «экран библиотеки в первом кадре — только store».

## Тесты (обязательные)

- Бэкенд: `artist_import_state_synced_on_transitions`, `import_heartbeat_does_not_bump_artist`.
- Клиент: экран артиста с `import = 'importing'` — блок в первом кадре, без сдвига при приходе деталей
  (положение сетки альбомов не меняется); с `import = null` — запроса нет.
- Сторож из п. 3.
