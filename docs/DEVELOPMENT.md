# Правила разработки Nimbus

Обязательны для любого изменения в репозитории — и для шагов `ROADMAP.md`, и для работ вне плана.
Если правило мешает сделать шаг правильно — правило меняется явно (правкой этого файла в том же коммите
и записью в Журнале `ROADMAP.md`), а не молча нарушается.

## 1. Определение готовности (Definition of Done)

Изменение готово, когда выполнено **всё**:

1. Реализовано всё из раздела «Что сделать» шага; ничего не оставлено в виде `TODO`/заглушек.
2. На каждое новое поведение есть тест, который падает без изменения. На каждый исправленный баг — регрессионный тест.
3. `just check` и `just test` проходят локально, без пропущенных (`#[ignore]`, `.skip`) тестов, добавленных этим изменением.
4. Покрытие не ниже порога (см. §4, §6) — `just cov` проходит.
5. Проведено ревью изменений по протоколу §7, найденное исправлено, тесты прогнаны повторно.
6. Обновлены: OpenAPI и сгенерированные типы (если менялся API), документация (`docs/`, `README.md`), статус и Журнал в `ROADMAP.md`.
7. Сделан коммит (§9). Рабочее дерево чистое.

Нельзя закрывать шаг с красными тестами, «временно» отключёнными проверками или пониженным порогом покрытия.
Если что-то заблокировано внешней причиной — статус `[~]` и строка `БЛОК:` в Журнале.

## 2. Общие принципы

- **Сначала прочитай, потом пиши.** Перед изменением модуля прочитай его целиком и его тесты.
  Код-скелеты в файлах шагов — ориентир: если реальный API библиотеки отличается, сверяйся с исходниками
  установленной версии (`~/.cargo/registry/src/…`, `client/node_modules/…`) и сохраняй контракт шага.
- **Контракты важнее реализации.** Эндпоинты, схемы БД, имена событий и настройки, описанные в шаге, —
  контракт для следующих шагов. Изменил контракт — обнови зависящие от него файлы `docs/roadmap/*.md`.
- **Минимальный дифф.** Не рефактори то, что не относится к шагу. Замеченное постороннее — в Журнал («Замечено»).
- **Никакой работы «на глаз».** Производительность — измеряется (тестом или цифрой в Журнале), надёжность — тестом на отказ.
- **Язык.** Комментарии, документация, сообщения коммитов — как в существующем коде (русские комментарии,
  английские идентификаторы и тексты ошибок API). Тексты интерфейса — только через i18n-словари.

## 3. Бэкенд (Rust)

### Код

- `cargo fmt`, `cargo clippy --workspace --all-targets -- -D warnings` — чисто. Линты уровня workspace
  (`[workspace.lints]`, шаг 25): `unwrap_used`, `dbg_macro`, `todo`, `unimplemented`, `print_stdout`,
  `print_stderr` — `deny` в боевом коде; `unsafe_code` — `forbid`. В тестах `unwrap` разрешён.
- `expect("…")` допустим только для **инвариантов**, нарушение которых — баг программы (а не данных/сети),
  с объяснением в строке. Для отравленных мьютексов — `unwrap_or_else(PoisonError::into_inner)` или `parking_lot`.
- Ошибки: `thiserror` в библиотечных крейтах, `anyhow` только в бинарнике. В API — `ApiError` с
  машинным `code`. Ошибку нельзя проглатывать: либо обработать, либо вернуть, либо залогировать с причиной,
  почему её можно игнорировать.
- **Любой внешний ввод-вывод — с таймаутом** (HTTP, торренты, ffmpeg, диск через `spawn_blocking`).
  Любой цикл ожидания — отменяемый (`CancellationToken`/`select!`).
- **Блокировки не держатся через `.await` сетевых операций.** Глобальная блокировка — только для
  обновления карты в памяти; длительная работа — под блокировкой уровня сущности (торрент, альбом).
- **Фоновые задачи отслеживаются**: каждый `tokio::spawn` либо в `JoinSet`/`TaskTracker` с остановкой при
  shutdown, либо с комментарием, почему это не нужно.
- **Задачи очереди идемпотентны**: повторный запуск той же задачи (после падения, дубликата, рестарта)
  не портит данные. Изменение нескольких таблиц — в транзакции.
- **Ограниченный параллелизм везде**, где есть внешний ресурс: семафор или лимитер, значение — из настроек.
- SQL — только в `crates/db` (репозитории). Миграции — только вперёд, новый файл `NNNN_*.sql`; существующие не редактируются.
  Каждая миграция совместима с данными предыдущей версии (значения по умолчанию, backfill).
- Логи — `tracing` со структурными полями (`album_id`, `torrent_id`, `info_hash`). Секреты не логируются.
- Публичный API крейта — с doc-комментарием «что и зачем», не «как».

### Что обязательно покрывается тестами

| Область | Вид тестов |
|---|---|
| Чистая логика (matcher, ранжирование, парсеры, лимитеры, редьюсеры состояний) | unit + property (`proptest`) для парсеров |
| Репозитории `db` | интеграционные на настоящем Postgres (`#[sqlx::test]`) |
| Обработчики задач (`worker`) | интеграционные: Postgres + фейки провайдеров/движка; счастливый путь, каждая ветка ошибки, повтор, исчерпание попыток |
| Очередь | конкуренция (`SKIP LOCKED`), heartbeat, восстановление после «падения», shutdown |
| Торрент-движок | локальный рой (`tests/swarm.rs`): метаданные, выбор файлов, стрим с seek, пауза/возобновление, раздача, рестарт, отказ пиров |
| HTTP API | `tower::ServiceExt::oneshot` по каждому эндпоинту: 2xx, валидация (4xx), авторизация (401), отсутствие сущности (404), отказ зависимости (5xx) |
| Внешние HTTP-сервисы | `wiremock` + фикстуры из реальных ответов в `tests/fixtures/`; тесты на живой сервис — только `#[ignore]` |
| Стриминг | Range (все формы), обрыв клиента, отсутствие пиров, failover, перекодирование (фейковый ffmpeg-скрипт) |

Правила тестов:

- Детерминизм: никаких `sleep` «на удачу». Время — `tokio::time::pause()`/`advance`, ожидание события — поллинг с дедлайном (хелпер `eventually`).
- Тест проверяет поведение, а не реализацию; одно утверждаемое поведение — один тест с говорящим именем.
- Фейки живут рядом с трейтом и переиспользуются (`fake_swarm`, `FakeFetcher`, `FakeProvider`), а не копируются по тестам.
- Тест не ходит в интернет и не зависит от порядка запуска; временные каталоги — `tempfile`.

### 4. Покрытие бэкенда

- Инструмент: `cargo llvm-cov` (`just backend-cov`), отчёт по строкам.
- **Цель: ≥ 90 % строк по workspace**; для `torrent`, `worker`, `matcher`, `db::repo::jobs`, `api::stream` — **≥ 95 %**.
- **Храповик:** порог хранится в `backend/coverage-threshold.txt` (целое число процентов). CI падает, если
  покрытие ниже порога. Порог можно только повышать: после шага, поднявшего покрытие, записать
  `floor(текущее) − 1`. Понижать порог запрещено.
- Исключать из покрытия можно только: `main.rs` (сборка зависимостей), модули `fakes`/`fake_swarm`,
  сгенерированный код. Каждое исключение — с комментарием.

## 5. Фронтенд (TypeScript, `client/`)

- Пакетный менеджер и раннер — **bun** (`bun install`, `bun run …`). Lockfile `bun.lock` коммитится.
  `npm`/`pnpm`/`yarn` в `client/` не используются.
- TypeScript `strict`, без `any` и `@ts-ignore` (исключение — с комментарием-причиной и `@ts-expect-error`).
  `bun run lint`, `bun run typecheck`, `bun run build` — чисто, без предупреждений.
- **Данные библиотеки читаются только из локального store** (память ← IndexedDB ← sync). Компонент экрана
  не делает `fetch` за артистами/альбомами/треками/плейлистами. Сетевые запросы из компонентов — только
  через слой `src/lib/api` и хуки TanStack Query (поиск, источники, настройки, загрузки).
- **Мутации оптимистичны**: сначала изменение в store, затем запрос; при ошибке — откат и toast.
- Навигация не должна ждать сеть: ни один маршрут не блокируется загрузкой данных.
- Логика отделена от React: store, sync, плеер, offline — чистые модули в `src/lib/**` с unit-тестами;
  компоненты тонкие.
- **Платформенные границы.** Клиент один для PWA и нативных оболочек (фаза 4 `ROADMAP.md`). Всё, что зависит
  от платформы, — только за интерфейсами: адреса и авторизация бэкенда — `src/lib/platform` (`apiUrl`, `wsUrl`,
  `authHeaders`); звук и системные элементы управления — `AudioEngine` (`src/lib/player/audio`); файлы на
  устройстве и их скачивание — `OfflineStorage`/`Downloader` (`src/lib/offline`). Прямые обращения к
  `HTMLAudioElement`, `navigator.mediaSession`, OPFS, литералы `'/api/…'` вне этих модулей запрещены линтом.
  Расширяешь интерфейс — обнови реализации всех платформ (или фейк и пункт в файле шага фазы 4).
- Дизайн: только токены из `src/styles` и примитивы `src/components/ui`. Никаких «магических» цветов и
  одноразовых стилей полей ввода. Каждый экран обязан иметь состояния: загрузка (skeleton), пусто, ошибка, офлайн.
  Светлая и тёмная тема, мобильная (≥ 360 px) и настольная вёрстка — обе обязательны.
- Доступность: интерактивные элементы — настоящие `button`/`a`/элементы форм или примитивы Ariakit;
  видимый фокус; `aria-label` у кнопок-иконок; управление с клавиатуры.
- Тексты — только через `useT()` и словари `src/lib/i18n/messages/*`. Новый ключ добавляется **во все** языки.
- Типы API — только сгенерированные (`bun run gen:api` из `client/openapi.json`); руками `schema.d.ts` не правится.

### 6. Тесты и покрытие фронтенда

- Unit и компонентные: **Vitest** + Testing Library + happy-dom (`bun run test`); IndexedDB — `fake-indexeddb`.
- Сценарные: **Playwright** против собранного клиента и мок-бэкенда (`bun run test:e2e`). Каждая
  пользовательская функция шага — минимум один сценарий.
- **Цель покрытия:** `src/lib/**` (store, sync, player, offline, i18n, api) — **≥ 90 % строк**;
  весь `src/` — **≥ 75 %**. Пороги — в `client/vitest.config.ts` (`coverage.thresholds`), действует тот же
  храповик: только вверх.
- Тесты не зависят от реального времени и сети: fake timers, мок `fetch`/WebSocket.

## 7. Ревью после каждой фичи (обязательно)

После реализации и **до** коммита:

1. Прогнать `just check && just test && just cov` (для шагов клиента — и `just client-e2e`). Красное — чинить, а не обходить.
2. Просмотреть **весь** дифф: `git status`, `git diff` (и `git diff --stat` для обзора). Если доступен skill
   `code-review` — запустить его на текущем диффе (уровень `medium`) и разобрать находки.
3. Пройти чек-лист:
   - **Корректность:** краевые случаи (пусто, ноль, очень много, повтор, гонка, отмена, рестарт посередине)? Ошибки не проглочены?
   - **Надёжность:** таймаут на каждом внешнем вызове? Блокировки не держатся через сеть? Фоновые задачи останавливаются? Задача идемпотентна?
   - **Данные:** миграция применима к существующей БД? Транзакция там, где меняется несколько таблиц? Индексы под новые запросы?
   - **Контракты:** OpenAPI/типы перегенерированы? События и DTO совпадают с описанными в шаге? Затронутые будущие шаги обновлены?
   - **Тесты:** каждая новая ветка покрыта? Есть тест на отказ? Нет `sleep`-ожиданий и флаки?
   - **Безопасность:** авторизация на новых эндпоинтах? Ввод валидируется и ограничен по размеру? Секреты не в логах/ответах? Пути файлов не выходят за каталог данных?
   - **UI (если есть):** обе темы, мобильная вёрстка, состояния загрузки/пусто/ошибка/офлайн, клавиатура, все языки.
   - **Чистота:** нет мёртвого кода, отладочного вывода, закомментированных блоков, случайных файлов.
4. Исправить найденное, **снова** прогнать п. 1.
5. В запись Журнала добавить строку «Ревью: …» — что нашлось и исправлено (или «замечаний нет»).

## 8. Команды

| Команда | Что делает |
|---|---|
| `just db-up` | Postgres для разработки и тестов |
| `just check` | fmt + clippy (бэкенд), lint + typecheck (клиент) |
| `just test` | все тесты бэкенда и unit-тесты клиента |
| `just cov` | покрытие бэкенда и клиента с проверкой порогов |
| `just backend-test` / `just backend-cov` | только бэкенд |
| `just client-test` / `just client-e2e` / `just client-build` | только клиент (появляются на шаге 36) |
| `just openapi` / `just client-gen-api` | OpenAPI → `openapi.json` → типы |
| `just e2e` | полный стек в Docker с фейковыми внешними сервисами |

Актуальный список — в `justfile`. До шага 36 клиентские рецепты относятся к старому `web/` (`web-check`, `web-build`).

## 9. Коммиты

- После любого изменения — коммит; рабочее дерево не остаётся грязным.
- Сообщение: `area: что сделано` (`backend: …`, `client: …`, `docs: …`); для шагов дорожной карты — `step NN: …`.
- Один шаг — один или несколько логичных коммитов; последний включает обновление `ROADMAP.md`.
- Секреты (`.env`) не коммитятся. Не пушить, если пользователь не просил.
